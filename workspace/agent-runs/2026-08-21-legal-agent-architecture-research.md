## Блок 1. Найденные паттерны Legal / Document Assembly Agents

### 1.1 Docassemble — ближайший реальный прецедент именно «интервью вместо формы» для юридических документов

**ЗНАЮ** (прямая проверка `docassemble.org/docs/documents.html` и файлов `jhpyle/docassemble` на GitHub). Docassemble — зрелая (с ~2013 года), широко используемая в legal aid и судах США open-source платформа для сборки юридических документов. Архитектура:

- Интервью описывается в **YAML**-файлах: блоки `question`/`subquestion`/`fields`/`mandatory`/`code`. Каждый вопрос — отдельный YAML-документ (разделены `---`). Следующий вопрос зависит от предыдущих ответов (`% if`/`% else` в тексте, ветвление по коду) — то есть это не статичная форма на N полей, а дерево вопросов, которое реально сокращается под конкретный случай (пример: если у пользователя один вариант, не спрашивать про содольщиков).
- Данные попадают в шаблон документа тремя способами: (а) Markdown → PDF/RTF/DOCX «с нуля»; (б) **DOCX-шаблон + Jinja2**, синтаксис `{{ variable }}` — это буквально тот же механизм, что и `docxtpl` (Jinja2 поверх .docx); (в) заполнение полей готового PDF-шаблона.
- Реальный пример из демо-репозитория (`courtfile.yml`) показывает типичный юридический флоу: сбор данных → блок `attachment` с шаблоном документа → показ готового документа пользователю → отдельное явное действие («нажмите кнопку, чтобы подать в суд») — то есть генерация черновика и его подтверждение/использование разнесены по времени, human-in-the-loop заложен в саму структуру интервью, а не добавлен сверху.

**Важная честная оговорка:** «диалог» в Docassemble — это адаптивный веб-визард (движок сам решает следующий вопрос по правилам YAML), а не LLM, ведущий разговор на естественном языке. Это ближайший по духу прецедент «интервью вместо формы» для юридических документов, но не LLM-агент. Прямого аналога «Docassemble + LLM внутри» с открытым кодом при поиске не нашлось.

Источники: [docassemble.org/docs/documents.html](https://docassemble.org/docs/documents.html), [jhpyle/docassemble courtfile.yml](https://github.com/jhpyle/docassemble/blob/master/docassemble_demo/docassemble/demo/data/questions/examples/courtfile.yml), [gblsma.github.io/docassemble-MotionTutorial](https://gblsma.github.io/docassemble-MotionTutorial/).

### 1.2 Anthropic's own Document Skills (`docx` skill) — реальный LLM-агентский паттерн работы с .docx

**ЗНАЮ** (прямая проверка raw-содержимого SKILL.md через зеркало `ComposioHQ/awesome-claude-skills/document-skills/docx/SKILL.md` — это опубликованная копия официального скилла Anthropic). Структура:

- **Workflow decision tree** прямо в теле SKILL.md: «читаешь документ → используй извлечение текста через pandoc»; «создаёшь новый → используй docx-js»; «редактируешь чужой документ, ИЛИ это юридический/деловой/государственный документ → используй Redlining workflow (для юридических — обязательно)».
- **Progressive disclosure**: сам SKILL.md — компактный роутер (~что делать и когда), глубокие инструкции вынесены в отдельные файлы (`docx-js.md` ~500 строк, `ooxml.md` ~600 строк), которые Claude читает только если реально нужен этот workflow — не грузит всё в контекст заранее.
- **Redlining (tracked changes) как обязательный для юридических документов режим** — прямое текстуальное совпадение с уже зафиксированным в проекте принципом «человек в контуре перед подписанием»: правки в документ вносятся как отслеживаемые изменения, а не как молчаливая перезапись текста.
- Скрипты (`unpack.py`/`pack.py`) — детерминированные инструменты, которые агент вызывает как код, а не как что-то, что LLM «придумывает» заново на каждой сделке.

**Честная оговорка (важно):** один из ранних поисковых AI-суммари утверждал, что этот же SKILL.md явно называет `docxtpl` и синтаксис `{{variables}}` как отдельный workflow «заполнение шаблона». В прямо прочитанном мной содержимом файла (workflow «Creating a new Word document») используется **docx-js**, а не `docxtpl` — я не нашёл в самом файле явного упоминания `docxtpl`. Возможно, это упоминание есть в другой версии/файле того же репозитория (`anthropics/skills`), который не открылся напрямую (404 на прямых путях, доступ был только через зеркало). Помечаю как **ПРЕДПОЛАГАЮ, не подтверждено первично** — не стройте на этом факте архитектурное решение; решение ниже (Блок 3) не зависит от того, использует ли официальный скилл Anthropic `docxtpl` буквально — оно опирается на то, что `docxtpl` уже работает в архивной версии этого проекта.

Источники: [github.com/anthropics/skills](https://github.com/anthropics/skills) (репозиторий подтверждён поиском, README подтверждает формат), содержимое SKILL.md — [raw.githubusercontent.com/ComposioHQ/awesome-claude-skills/master/document-skills/docx/SKILL.md](https://raw.githubusercontent.com/ComposioHQ/awesome-claude-skills/master/document-skills/docx/SKILL.md), общее описание Agent Skills — [anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).

### 1.3 Microsoft Agent for Contract Processing Solution Accelerator — реальный вендорский паттерн «агент вместо формы» для контрактов

**ЗНАЮ** (прямая проверка README репозитория). Это официальный Microsoft solution accelerator (Copilot Studio) под сборку/согласование NDA:

- Сбор данных — **разговор в Teams** с агентом, структурированные варианты через Adaptive Cards вместо «сырых» веб-форм (то есть тоже «интервью через диалог», как и просит владелица, только на платформе Copilot Studio, а не на LLM-агенте общего назначения).
- Шаблоны хранятся в SharePoint как библиотека документов, с разделением на неподписанные шаблоны / черновики / финальные подписанные — концептуально то же самое, что уже реализовано в проекте как `registry.json` с `draft/active/archived`.
- Явный **этап человеческого утверждения** («сотрудник проверяет черновик и остаётся доволен») перед тем, как документ уходит на подпись (DocuSign) — с явно обозначенной возможностью добавить ещё один шаг внутреннего юридического согласования.

Это ближайший найденный «крупновендорский» пример структуры «диалог → структурированные данные → шаблон → человек утверждает → подпись», хотя сама технология (Copilot Studio/Power Platform, закрытая) не подходит для прямого переноса — полезен только паттерн, не код.

Источник: [github.com/microsoft/Agent-for-Contract-Processing-Solution-Accelerator](https://github.com/microsoft/Agent-for-Contract-Processing-Solution-Accelerator).

### 1.4 Community-репозитории Claude-скиллов под юридические задачи — подтверждают структуру `skills/` + `templates/`, но не являются проверенным эталоном

**ПРЕДПОЛАГАЮ по надёжности** (репозиторий не от Anthropic, авторство/качество не проверено, вижу только README через WebFetch): `zubair-trabzada/ai-legal-claude` — пакет из 14 скиллов (каждый со своим SKILL.md) + 5 параллельных агентов-ревьюеров + `templates/`. Явный дисклеймер внутри — «не является юридической консультацией», требует проверки юристом перед подписанием. Полезно как *подтверждение существования паттерна* «много узких SKILL.md-скиллов + отдельная папка шаблонов», но не как эталонный код для копирования — это любительский проект, не production-grade.

Источник: [github.com/zubair-trabzada/ai-legal-claude](https://github.com/zubair-trabzada/ai-legal-claude).

### 1.5 Вывод по Блоку 1

Готового open-source «Legal Document Assembly Agent» именно под LLM-агента с чистым AGENTS.md для сборки договоров недвижимости **не найдено** — прямо, без додумывания. Ближайшие по духу существующие паттерны:

1. **Docassemble** — зрелый юридический прецедент «адаптивное интервью → DOCX/Jinja2-шаблон», но без LLM в контуре сбора данных.
2. **Anthropic docx skill** — зрелый LLM-агентский паттерн работы именно с .docx (создание/редактирование/redlining), с обязательным tracked-changes режимом для юридических документов, но не заточен на «многодокументный комплект по правилам состава».
3. **Microsoft Copilot Studio accelerator** — зрелый вендорский паттерн «диалог вместо формы + человек утверждает черновик» для контрактов, но на закрытой платформе.

Ни один из них не покрывает целиком задачу проекта («динамический комплект документов по правилам, диалоговый сбор переменного числа участников, docxtpl-реестр»). Предложение Блока 3 — комбинация этих трёх паттернов поверх уже работающего движка (docxtpl + registry.json), не изобретение с нуля и не слепое копирование одного чужого репозитория.

## Блок 2. Разбор структуры AGENTS.md на реальных примерах

### 2.1 Формальная спецификация AGENTS.md

**ЗНАЮ** (прямая проверка `agents.md`). Ключевые факты:

- Формат — **простой Markdown, без обязательных полей, без YAML frontmatter**. «README для агентов»: то, что человеку в README читать не нужно (команды сборки, стиль кода, границы поведения), но агенту — нужно каждый раз.
- Используется 60k+ open-source проектами, поддержан 30+ инструментами (не только Claude — Codex, Copilot и др.) — то есть это в первую очередь стандарт для **coding-агентов**, не для агентов прикладных задач вроде сборки договоров.
- Типовые разделы: project overview, build/test commands, code style, testing instructions, security considerations, dev environment tips, PR/commit guidelines.
- В монорепозиториях — вложенные AGENTS.md по подпроектам; агент читает ближайший файл к тому месту, где работает.

Источник: [agents.md](https://agents.md/).

### 2.2 Что AGENTS.md не даёт «из коробки» для этой задачи

AGENTS.md как формат — это конвенция про *coding*-агентов (что собрать, как тестировать, какой стиль кода). Он не содержит встроенной идеи «роль / вход-выход / границы / доступные инструменты для прикладной задачи» — это нужно спроектировать самим, взяв нужную часть идеи (человекочитаемый контракт в корне репозитория) и наполнив её содержанием, подходящим для агента, который *делает* работу (собирает документы), а не *пишет код*.

### 2.3 Более подходящий формальный образец — спецификация Agent Skills (SKILL.md)

**ЗНАЮ** (прямая проверка `anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills` и содержимого реального SKILL.md, см. Блок 1.2). Формат SKILL.md ближе к тому, что нужно для «агентского контракта прикладной задачи»:

- Обязательные поля во frontmatter: `name`, `description` — по `description` агент решает, когда вообще открывать этот файл.
- Тело — конкретные инструкции: decision tree (что делать в каком случае), явные workflow-шаги, явные запреты/обязательные режимы (пример — «Redlining workflow обязателен для юридических документов»).
- Трёхуровневая **progressive disclosure**: (1) имя+описание — всегда в контексте; (2) полный SKILL.md — когда Claude решил, что это релевантно; (3) отдельные reference-файлы и скрипты — подгружаются по требованию, не заранее.

### 2.4 Вывод по Блоку 2

Ни один из двух форматов не подходит один в один — предлагается гибрид: **AGENTS.md-подобный контракт** (роль/границы/вход-выход, как ожидает от репозитория владелица — она сама так и назвала файл в запросе) **, написанный по принципу progressive disclosure из SKILL.md** (сам контракт компактный, детали — в отдельных reference-файлах: правила состава комплекта, схема Deal, — чтобы агент не грузил в контекст сразу всё при каждом обращении).

## Блок 3. Предложение архитектуры для этого проекта

### 3.0 Главный принцип: не переизобретать движок

Механизм подстановки данных в .docx (`docxtpl` + `registry.json` с правилом «один `active`-шаблон на пару document_type×deal_type», сама рендер-логика) **уже построен и работает** в `AI Legal Constructor/archive/web_proto/app/` — проверено прямым чтением кода:

- `archive/web_proto/app/generator.py` — рендерит через `from docxtpl import DocxTemplate`, собирает контекст под конкретный документ, использует `active_template_path()` и `build_document_set()`.
- `archive/web_proto/app/registry.py` — реестр `templates_docx/registry.json`, буквально реализует правило хендоффа §5 («на пару document_type×deal_type только один `active`»), кидает `TemplateNotFound` при нарушении.
- `archive/web_proto/app/rules.py` — правила состава динамического комплекта (сколько комиссий, нужен ли акт, нужны ли согласия) — это прямая реализация хендоффа §5.
- `archive/web_proto/templates_docx/*.docx` + `registry.json` — сами шаблоны и реестр, уже с версиями v1.

**Меняется не движок, а то, как в него попадают данные** — раньше через 4 Flask-экрана с HTML-формами (заархивировано из-за структурной путаницы двух `<form>` на одном экране, стёршей ввод), теперь через диалог с агентом. `generator.py`/`registry.py`/`rules.py` переносятся в новую структуру почти без изменений (снять Flask-обвязку, HTML-шаблоны экранов и веб-роуты — не нужны; заодно исправить найденный на живом тесте дефект кодировки кириллицы, хендофф §12а — он актуален для любого способа ввода, не только веб-формы).

### 3.1 Структура репозитория

├── templates_docx/                # ПЕРЕНОС БЕЗ ИЗМЕНЕНИЙ из archive/web_proto/templates_docx
│   ├── registry.json               #   тот же реестр active/draft/archived
│   └── *.docx                      #   те же файлы (комиссия, основной_договор, акт, согласие) × (аренда/продажа)

│   ├── generate_package.py         #   без Flask — это детерминированные инструменты агента (как unpack.py/pack.py

├── examples/                      # few-shot-примеры ДЛЯ АГЕНТА (не для человека) — как выглядит хорошо
│   ├── example_deal_rent_2owners.json   #   заполненная структура Deal (§4) на характерном случае
│   │                                     #   (2 собственника в долях + 1 арендатор, один в браке)
│   └── example_dialogue.md              #   пример диалога от старта сделки до готового комплекта —

│   └── <deal_id>/

│       └── confirmations.md          #   лог того, что именно подтвердил человек и когда — OCR-поля (§Phase 1.1),
│                                      #   AI-сформулированные особые условия (§5.1) — обе точки, где хендофф

└── output/                         # готовые .docx комплекты
    └── <deal_id>/

Отдельно от предложенной новому владельцу структуры: `archive/web_proto/` не трогается, остаётся как есть (рабочий, провалидированный код, задокументированный `ARCHIVED.md`) — новая структура **переносит** из него нужные файлы, не удаляет и не переписывает архив.

### 3.2 AGENTS.md — содержание контракта

Компактный корневой файл (по духу — как советует спецификация agents.md: без обязательных полей, простой Markdown), примерное содержание по разделам:

**Роль.** Агент собирает комплект документов сделки с недвижимостью (аренда/продажа) для агентства Мегаполис: узнаёт у пользователя данные о сделке и участниках через диалог, определяет нужный состав документов по правилам (см. `docs/deal-schema.md`), рендерит .docx из активных версий шаблонов `templates_docx/registry.json`, сохраняет в `output/<deal_id>/`.

**Вход.** Естественный диалог с пользователем (текст, по одному логическому блоку данных за раз — не запрашивать всё сразу); опционально — фото/скан документа участника (Phase 1.1), обрабатывается через `ocr_extract` инструмент, результат — предложенные значения полей, никогда не пишется в `deal.json` без явного подтверждения пользователя.

**Выход.** Набор .docx-файлов в `output/<deal_id>/` + отчёт о полноте данных перед генерацией + для каждого AI-сформулированного особого условия (§5.1) — явный шаг подтверждения текста пользователем до вставки в файл.

**Границы (что агент НЕ делает)** — прямое отражение хендофф §10 «Что НЕ делать» и §3 «Что не является системой»:
- не выбирает и не переписывает юридическое содержание шаблонов (это Мария/юрист);
- не определяет самостоятельно, при каких условиях согласие обязательно по закону — использует уже заданные `consent_flags`, не изобретает новые основания;
- не переводит шаблон из `draft` в `active` самостоятельно — это отдельное решение владелицы вне диалога сборки конкретной сделки;
- не подписывает документы и не отправляет их куда-либо без явной команды;
- не вставляет AI-сформулированный текст особого условия в файл без явного подтверждения человеком.

**Доступные инструменты (skills/scripts):**
- `registry_lookup(document_type, deal_type)` — найти активный шаблон, вернуть ошибку по образцу `TemplateNotFound`, если не найден/дублирован;
- `check_completeness(deal)` — по правилам `docs/deal-schema.md` определить итоговый список документов и каких данных не хватает под каждый;
- `generate_package(deal)` — отрендерить все документы комплекта через `docxtpl`, сохранить в `output/<deal_id>/` с понятными именами;
- `ocr_extract(image)` *(Phase 1.1, если решение по локальный OCR/Claude Vision принято — хендофф §9)* — вернуть предложенные поля, не пишет напрямую.

**Формат данных.** `deal.json` — единственный источник истины для рендеринга; схема = хендофф §4, зафиксирована отдельно в `docs/deal-schema.md`, а не дублируется внутри AGENTS.md (progressive disclosure — агент подгружает схему по необходимости).

### 3.3 Диалоговый флоу сбора данных — пошагово, без веб-форм

Логика состава комплекта и правила согласий **не меняются** (хендофф §4–5, LOCKED) — меняется только то, как данные попадают в `deal.json`.

1. **Тип сделки и объект.** Агент спрашивает: аренда или продажа → адрес, кадастровый номер, площадь, тип объекта, основание права собственности, обременения — блоком, но не всё одним сообщением-простынёй, а с уточняющими вопросами по ходу (как в Docassemble — следующий вопрос по ситуации, не жёсткий список).
2. **Участники — по одному, переменное число.** Агент спрашивает: «Кто участвует в сделке со стороны объекта? Со стороны контрагента?», добавляет участников по одному, на каждого — роль, ФИО, паспортные данные, представитель (если по доверенности), доля (если долевая), флаги `is_married`/`is_minor`/`has_other_co_owners`. После каждого участника — «Есть ещё участники с этой стороны?» вместо фиксированной пары полей (прямое соответствие хендофф §4, «не два фиксированных поля, а динамический список»).
   - Если пользователь прикладывает фото паспорта/выписки ЕГРН — агент вызывает `ocr_extract`, показывает распознанное как черновик, ждёт подтверждения/правки, только после этого пишет в `deal.json` (тот же human-in-the-loop принцип, что уже зафиксирован в хендоффе для OCR, не решается заново здесь).
3. **Условия сделки.** Цена, порядок расчётов, срок/дата передачи, комиссия по каждому участнику. Особые условия (§5.1): агент называет типовые варианты (животные, рассрочка комиссии, субаренда и т.п. — библиотека snippet-шаблонов) как вопрос-подсказку («подходит что-то из типового: …?»), плюс принимает свободный текст → формулирует пункт → показывает точный текст на подтверждение/правку, прежде чем занести в `deal.json` как согласованное особое условие.
4. **Проверка полноты.** Агент вызывает `check_completeness` — определяет по правилам итоговый список документов (5–10 штук по хендофф §5) и явно называет, каких данных не хватает под какой конкретно документ, если есть пробелы; не переходит к генерации, пока пробелы не закрыты или пользователь явно не согласился отложить документ.
5. **Генерация.** Только после подтверждения полноты — `generate_package`; агент показывает итоговый список файлов, которые собирается создать (сколько комиссий, какие акты/согласия), пользователь подтверждает состав до фактического рендера — дополнительная точка проверки на случай ошибки во флагах согласий (хендофф §7, «ошибка ввода флага должна быть видна человеку до подписания»).
6. **Результат.** Файлы сохраняются в `output/<deal_id>/` с понятными именами; агент явно напоминает, что это черновики для юридической проверки перед подписанием — не меняет уже согласованный принцип «человек в контуре перед подписанием» (хендофф §7).

### 3.4 Что остаётся открытым (не решается этим исследованием)

- **[УТОЧНИТЬ]** — точный список оснований для `consent_flags` (хендофф §9) — решает юрист, вне контура этого исследования.
- **[УТОЧНИТЬ]** — локальный OCR или Claude Vision для Phase 1.1 (хендофф §9) — влияет на то, как именно реализован инструмент `ocr_extract`, но не на структуру диалога выше (в обоих случаях — «распознал → предложил → человек подтвердил»).
- **[УТОЧНИТЬ]** — технический носитель самого диалогового агента (Claude Code напрямую / Claude Agent SDK-приложение / что-то ещё) — это инженерное решение следующего шага, не предмет этого исследования; предложенная структура репозитория (AGENTS.md + templates_docx/ + scripts/ + examples/ + deals/ + output/) не привязана к конкретной реализации носителя.

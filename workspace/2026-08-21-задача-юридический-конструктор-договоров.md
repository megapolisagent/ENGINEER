## Обновление 2026-08-21 (владелец: «он подкрепляет его но пишет что не выбран» + вопрос про дальнейший поток)

Живой тест показал: файл видимо прикрепляется, но сервер всё равно отвечает «Файл не выбран». Первая гипотеза (автоотправка формы при drag/paste мешает) не подтвердилась при повторной проверке — переделала JS без автоотправки (явная подпись «Выбран файл: …», нажатие «Распознать» остаётся осознанным шагом), но сама ошибка осталась.

**Найден настоящий корень (после нескольких неверных гипотез, каждая проверена и отброшена, не выдана за факт):** `if file` в Python вызывает `bool(FileStorage)`, а в Werkzeug это равно `bool(filename)`, не наличию содержимого. При вставке из буфера/перетаскивании браузер может прислать файл с пустым `filename`, хотя байты реально есть — старая проверка `file.read() if file else b""` в этом случае теряла файл, даже не пытаясь прочитать. Исправлено на `file is not None` — воспроизведено через `Flask test_client` с настоящей картинкой и пустым именем файла до фикса (ошибка) и после (адрес/площадь корректно распознались, ошибок нет). Обычная загрузка через проводник (не пустое имя) — тоже проверена, не задета.

По второму вопросу владельца («когда распознает — что дальше?») — ответ дан прямо в чате, не только здесь: распознанные поля предзаполняют ту же форму на экране (адрес/кадастровый номер/ФИО и т.д.), ничего не сохраняется автоматически; сохранение происходит только по уже существующей кнопке «Далее»/«+ Добавить участника», которую владелец нажимает осознанно после проверки/правки полей — это не новая логика, тот же принцип, что был согласован в исходном grill-раунде Phase 1.1.

Рекомендация исследования — Вариант A (доработка локального пути): заменить Tesseract на **PaddleOCR PP-OCRv5 mobile** (бесплатный, CPU, обучен на кириллице), Вариант B (полностью облачные Vision API) отклонён из-за 152-ФЗ — ни один из трёх провайдеров (Claude/GPT-4o-mini/DeepSeek) не предлагает обработку персональных данных на серверах в РФ, что закон требует для ПДн граждан РФ.

### Переход на PaddleOCR — блокер окружения

`pip install paddlepaddle` не находит колёс для Python 3.14 (стоит на машине владельца) — PaddlePaddle пока не поддерживает эту версию Python. Не решаю это в обход (не понижаю системный Python, не форсирую несовместимую установку) — ставлю отдельный Python 3.12 через winget рядом с существующим, специально под виртуальное окружение для OCR-слоя. Существующий Python 3.14 и всё остальное приложение это не затрагивает.

### Собрано и проверено

- Виртуальное окружение `venv312/` (Python 3.12) + `paddlepaddle` + `paddleocr`, отдельно от основного приложения (Python 3.14) — мост между ними через `subprocess` (одноразовый запуск воркера на каждое распознавание, без постоянного сервиса — соразмерно низкой частоте запросов Phase 1).
- `scripts/paddle_ocr_worker.py` — отдельный процесс, печатает результат после маркера, чтобы служебные логи PaddleOCR не попали в текст документа.
- **Реальная поломка при первом прогоне (не гипотеза):** `PP-OCRv5_server_det` (авто-выбор по умолчанию) + oneDNN падает на этой машине с `NotImplementedError` внутри PaddlePaddle — исправлено явным выбором мобильных моделей (`PP-OCRv5_mobile_det` + `eslav_PP-OCRv5_mobile_rec` — специализирована на кириллице/восточнославянских языках) и `enable_mkldnn=False`.
- **Вторая реальная поломка**, найденная не сразу (несколько неверных гипотез отброшено по ходу, ни одна не выдана за факт): дочерний процесс печатал кириллицу в кодировке консоли Windows, а не в UTF-8, если сам Flask-сервер запущен без `PYTHONIOENCODING=utf-8` в окружении (обычный случай — `python run.py` без этой переменной) — часть кириллических слов (адрес, площадь) приходила как заменяющие символы и не проходила через regex-парсер, при этом цифровые поля (кадастровый номер) выживали, что маскировало проблему. Исправлено — переменные окружения `PYTHONIOENCODING`/`PYTHONUTF8` задаются явно в самом вызове `subprocess.run`, не полагаясь на окружение запуска сервера.
- **Прямое сравнение на том же случае, где Tesseract промахнулся:** кадастровый номер «77:03:0007007:4321» — Tesseract вернул «/ /:03:000 7/00 /:4321» (искажённые цифры), PaddleOCR — точно верно, несколько независимых прогонов подряд. Это ожидаемо по рекомендации исследования, но проверено фактическим прогоном, не принято на веру.
- Все три прежних smoke-теста (`smoke_test.py`, `http_smoke_test.py`, `ocr_smoke_test.py`) перепрогнаны после перехода — регрессий нет.
- Tesseract/`tessdata/` убраны из репозитория как более не используемые; `requirements.txt` (основное приложение) и новый `requirements-ocr.txt` (окружение venv312) разведены по смыслу.

**Независимая проверка (M1 Reviewer, haiku) — первый прогон: VERDICT FLAG.** Нашла реальный недочёт: фикс `bool(FileStorage)` был применён только к маршруту `scan_egrn` (экран 1), маршрут `scan_passport` (экран 2, загрузка фото паспорта) остался со старым багом `if file` — тот же «прикрепляет, но пишет не выбран» был бы всё ещё жив на экране участников. Исправлено сразу (`app/main.py`, строка с `data = file.read()` в `scan_passport`), проверено воспроизведением того же сценария через `Flask test_client` — дошло до этапа распознавания, файл больше не теряется. Полный регресс (`smoke_test.py`) перепрогнан — OK.

**Повторная проверка (M1 Reviewer, haiku) — VERDICT: OK.** Подтверждено: оба маршрута (`scan_egrn`, `scan_passport`) используют `file is not None`, ни одного места с прежним `if file` не осталось.

# Задача: технический план Telegram-мост → headless Claude Code на VPS

Дословный контекст владельца (2026-09-04): «Мы строим автономную экосистему агентов на базе
Claude Code на VPS с управлением через Telegram, сохраняя локальную дисциплину (HOME.md,
DECISIONS.md, жесткую структуру скиллов). Сторонние коробочные решения вроде Hermes ставить
не будем... нам нужно изучить передовой опыт сообщества.» Три части поручены: (1) ресерч
реальных OSS-паттернов — сделала Researcher, `AI Intelligence/knowledge/evidence/2026-09-04-
telegram-headless-claude-code-bridge-vps-logging.md`; (2) аудит безопасности/чистоты найденных
решений — ниже; (3) конкретный план внедрения — ниже.

## Аудит найденного

**`RichardAtCT/claude-code-telegram`** — сильные стороны: multi-user whitelist, лимит стоимости
на пользователя (`CLAUDE_MAX_COST_PER_USER`), rate limiting, HMAC-подпись вебхуков. Слабое
место для нас: нет встроенного деплоя как persistent-процесса — пришлось бы строить самим.
Multi-user модель — лишняя сложность, у нас один владелец, не команда.

**`Mark-Life/telegram-claude-codex`** — сильные стороны: single-user whitelist (`ALLOWED_USER_ID`)
— меньше поверхности атаки, ровно наш случай; встроенный `systemd`-деплой (`service:install`)
с `journald` + `loginctl`-lingering; long-polling, не вебхук — не нужно открывать входящий порт
на VPS вообще, чем меньше открытых портов, тем меньше поверхность атаки; умеет и Claude SDK
in-process, и спавн `codex exec` — совместимо с нашей многоагентной архитектурой (разные
процессы под разных агентов). Слабое место: нет лимита стоимости и rate limiting — реальный
риск, учитывая, что headless-вызовы этой ночью реально стоили $2.62 и $0.94 за один заход.

**Ни один не тащит тяжёлую веб-панель** — у RichardAtCT FastAPI-слой опционален и выключен по
умолчанию (`ENABLE_API_SERVER=false`), у Mark-Life веб-слоя нет вообще. Оба проходят требование
«не тащат шелуху».

**systemd-паттерн из gist (Hermes-пример)** — взят только как универсальный шаблон юнита
(`Restart=on-failure`, `RestartSteps`, `journald`, `loginctl enable-linger`) — сам Hermes не
устанавливается, это отдельно подчёркнуто и в находке Researcher, и здесь.

## Рекомендуемая архитектура — синтез, не копия одного репозитория

**База: `Mark-Life/telegram-claude-codex`**, форкнутый в `megapolisagent` (тот же паттерн, что
уже применяется к скачанным Skills — не зависеть от чужого неподдерживаемого репозитория
напрямую), не установленный как чужой пакет.

**Добавить сверху (закрывает найденный пробел):**
1. **Жёсткий дневной лимит стоимости** (идея из RichardAtCT, реализация своя — считать через
   `total_cost_usd` из `--output-format json`, который мы уже читаем всю эту сессию) — при
   превышении порога бот отвечает «лимит на сегодня достигнут» и не запускает новый вызов,
   не тихо продолжает списывать.
2. **`ALLOWED_USER_ID` = только Telegram ID владельца.** Никакой multi-user модели не нужно.
3. **Каждый вызов, инициированный ботом, получает `task_id` и запись в
   `ENGINEER/knowledge/delegation-ledger.md`** — тот же механизм, что уже реально работает
   для headless-дисптечей этой ночи, просто источник вызова меняется (бот, не Engineer вручную).
4. **Working directory бота ограничена списком известных путей агентов** (`AI Marketing
   Strategist`, `AI Avitolog`, `AI Traffic Manager`, `AI Intelligence`, `ENGINEER`) — бот не
   может запустить `claude -p` в произвольной папке VPS по запросу из чата.
5. **Изоляция скриптов** (`instructions/external-script-safety.md`, уже существующее правило
   дома) — применяется на VPS так же, как на локальной машине: непроверенный скрипт — сначала
   в отдельной scratch-папке, не в рабочей папке агента.

## Пошаговый план внедрения

**Этап 1 — VPS и авторизация.** Арендовать Linux VPS (Ubuntu). Установить Claude Code CLI,
пройти авторизацию под аккаунтом владельца (`claude login` или API-ключ — решить, что именно,
отдельным вопросом владельцу перед этим этапом, не решать самостоятельно). Установить Bun
(нужен форкнутому мосту).

**Этап 2 — Мост.** Форкнуть `Mark-Life/telegram-claude-codex` в `github.com/megapolisagent/`,
задать `ALLOWED_USER_ID`, добавить лимит стоимости и task_id/ledger-хук (пункты 1 и 3 выше).

**Этап 3 — Деплой.** `bun run service:install` (готовый скрипт репозитория) → `systemd`
user-юнит + `journald` + `loginctl enable-linger`. Проверить `service:status`/`service:logs`.

**Этап 4 — Ограничение рабочих директорий.** Пункт 4 выше — явный список путей, не свободный ввод.

**Этап 5 — Один реальный сквозной тест до продакшена.** Одно сообщение с телефона → бот
вызывает `claude -p` в папке одного из агентов (например, Traffic Manager, самый безопасный —
советник, не исполнитель) → результат приходит обратно в Telegram. Только после этого
подключать cron-задачи для мониторинга по расписанию — не наоборот.

**Этап 6 — Cron-мониторинг.** Только после Этапа 5. Отдельный вопрос, не решённый здесь: как
формулировать критерий достаточности для задачи, которую никто не подтверждает живьём каждую
ночь (`pre-task-check.md` требует показывать бриф владельцу перед существенным исследованием) —
предлагается: заранее одобренный, фиксированный список ночных брифов с критериями (утверждается
владельцем один раз, не каждую ночь), а не разовое подтверждение на каждый прогон.

## Открытые вопросы, не решённые в этом плане

- Способ авторизации Claude Code на VPS (логин vs API-ключ) — решение владельца.
- Как cron-брифы проходят Delegation Gate без живого подтверждения каждый раз (Этап 6) —
  предложение выше, не Locked.
- Стоимость VPS + реальная стоимость headless-вызовов в масштабе (не оценивалась численно).

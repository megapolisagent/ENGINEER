# Pipeline Architecture — эталонный стандарт производственного конвейера

> Закон для любой системы, где объём боевого контура оправдывает конвейер: скрипты как костяк, узкие субагенты Claude Code — только на развилках неопределённости. Зафиксировано 2026-09-09 по итогам разбора трёх реальных агентов (CMO, Авитолог, Трафик-менеджер); дополнено тем же днём разбором вебинара про закупочную систему («откуда рвётся цепочка на третьем звене») — рациональные звенья, проверенные независимо от источника, отмечены отдельно. Дополнено 2026-09-10 вторым проходом по тому же вебинару (более детальные скриншоты CLAUDE.md системы планирования закупок) — изоляция импортов между стадиями, ровно два шва для тестов, механика staging/commit, `UNSTAGED_ARTIFACTS`, дублирование закрытого словаря как `FORM` рядом с вызовом агента, докстрока «что здесь спрятано», критерий пропуска стадии.

---

## 0. Применимость — когда этот стандарт вообще включается

Полный номерной конвейер (§5) нужен только там, где за один прогон обрабатывается реальный объём однотипных сущностей (SKU, лоты, лиды, заявки) — там, где в Scope паспорта вообще есть что писать как число N.

**Не годится для советующих/разговорных агентов**, где вход — один вопрос владельца за раз, а не пакет сущностей. Пример на 2026-09-09: CMO и Трафик-менеджер отвечают на один запрос за раз — им нужен только слой `tools/` внутри skill (§3), не 12 пронумерованных стадий. Форсировать номерную стадийность на такой агент — переинженеринг по `yagni-ladder`, не следование стандарту.

Признак, что пора переходить от «просто `tools/`» к полному конвейеру §5 — не «система выглядит солидно», а реальный объём: несколько десятков+ сущностей за прогон, конфликтующие данные, которые стоит явно классифицировать, реальная параллельность разбора аномалий. Пока объём — единицы (пример: Авитолог на 2026-09-09 — 1 активный лот в `data/lots/`), из этого стандарта внедряются только принципы §1, §3, §4, §6 (Script-First, слои скилла, `config.json`, контракт вывода субагента) — без стадийной нумерации и без параллельных subagent-пулов, которые нечем занять.

**Три дополнительных фильтра «стоит ли вообще собирать конвейер под эту задачу»** (даже если объём формально есть):
1. Задача повторяется не реже раза в неделю — разовую дешевле сделать руками.
2. Вход уже существует файлом/выгрузкой — если данные сначала нужно где-то собрать, это отдельная задача, решается первой.
3. Результат проверяется глазами за минуту — иначе непонятно, система реально работает или красиво врёт.

## 1. Script-First — детерминированный костяк, агент только на развилке

Задача, которую можно полностью описать блок-схемой без единого узла «прочитать и понять смысл» — код, не агент. Агент нужен только там, где узел требует интерпретации неструктурированного входа или суждения без единственно верного ответа.

Практически: скрипты закрывают детерминированную рутину (расчёты, валидация форматов, сборка фида/дашборда) — целевая доля такой рутины в производственном контуре высокая (ориентир ~85%, не жёсткое число, а сигнал: если агент разбирает почти каждую позицию вручную — граница агент/скрипт проведена неверно). Субагенты подключаются только на реальных развилках: спорные данные, аномалии, финальный аудит перед публикацией.

**Маршрутизация между ролями — тоже код, не отдельный агент-диспетчер.** Решение «кому из субагентов отдать эту позицию» — обычно набор пороговых правил с числами (см. пример в §5: 8 типовых ситуаций → 4 адресата, чисто табличная развилка), не отдельная агентская роль «менеджер-распределитель». Заводить агента специально для маршрутизации — тот же переинженеринг, что агент вместо скрипта на любом другом детерминированном узле.

Слой `tools/` внутри одного `SKILL.md` (§3) и пронумерованный конвейер (§5) — один и тот же принцип на разных масштабах. Каждая стадия конвейера — либо вызов детерминированного кода из общего ядра (расширенный `tools/`, вынесенный за пределы одной папки, потому что стадии делят между собой факты и контракт), либо вызов узкого субагента с жёстко объявленными tools — Read/Write, не «всё».

**Рендер — та же граница, применённая к вёрстке.** `render.py` не генерирует HTML/CSS на лету — берёт готовый каркас из `templates/` (плейсхолдеры под данные) и инъецирует туда вычисленный JSON. Агент/LLM никогда не участвует в сборке разметки боевого артефакта — это убирает риск сломанных стилей и непредсказуемой вёрстки на дашборде, тот же риск, что хардкод порога в коде (§4), только применённый к визуальному выводу, а не к числу.

## 2. Обязательная структура паспорта CLAUDE.md

Любая система, подпадающая под этот стандарт (§0), ведёт `CLAUDE.md` по следующей структуре — без урезания разделов:

1. **Шапка (Паспорт проекта)** — название, Scope одной фразой (объём боевого контура: сколько сущностей обрабатывается), ключевой баланс (скрипты считают X% детерминированно, N субагентов разбирают только спорные случаи), финальный артефакт на выходе.
2. **Команды запуска (Bash)** — версия среды, зависимости (по возможности — standard library), команда сквозного прогона из корня, команда тестов (`unittest discover` или аналог), флаги конфигурации (`--config`, `--data-dir`, `--out-dir`), явное разграничение — какие этапы код, какие агентные.
3. **Карта проекта** — компактное дерево с ролью каждой папки: `core/` (или `pp/`) — ядро расчётов, один модуль = один этап конвейера, имя файла 1:1 к названию стадии (`validate.py`, `facts.py`, `triage.py`, `merge.py`, `render.py`, плюс `pipeline.py` — оркестратор сквозного прогона); `tests/` (зеркалит модули ядра); `.claude/agents/` (декларации узких субагентов со строго объявленными tools); `.claude/skills/<name>/SKILL.md` (оркестратор агентных этапов — порядок, параллелизм, обработка отказов); `templates/` (готовые HTML-каркасы с плейсхолдерами — принцип шаблонизации см. §1); `out/` и `runs/<date>/` (механизм ротации — §8); `docs/adr/` (архитектурные решения по коду конвейера — назначение и граница с `knowledge/` см. ниже); `config.json`.
4. **Таблица «Зачем трогать»** — Файл | Зона ответственности (вход → выходной контракт), по одной строке на ключевой модуль. Модель сразу понимает, куда идти при правке конкретной механики.
5. **Архитектура сквозного конвейера** — пронумерованный протокол по образцу §5 (только если объём оправдывает, см. §0). **Паспорт и плейбук не дублируют друг друга: `CLAUDE.md` показывает ЧТО есть — карту стадий и разделение скрипт/агент; точные CLI-команды и параметры каждой стадии живут в оркестраторном `SKILL.md` (§3, слой Instructions) — это КАК и чем именно вызывается каждый шаг.**
6. **Архитектурные границы и изоляция** — по образцу §7.
7. **Соглашения кода** — пороги только через `config.json` (§4); стандартные форматы (UTF-8, разделители, ISO-даты `YYYY-MM-DD`); закрытые словари значений (константы-enum), с которыми сверяются ответы агентов; пустое значение нигде молча не становится нулём — помечается `None` с фиксацией причины.
8. **Gotchas** — по образцу §8.

**`docs/adr/` — архитектурные решения по коду конвейера, граница с `knowledge/` зафиксирована и обязательна.** Пронумерованные markdown-файлы (`0001-...`, `0002-...`) с обоснованием инженерных решений внутри `core/`: почему `validate` стоит перед `audit`, а не наоборот; почему выбран такой формат промежуточного JSON; какие технические альтернативы отброшены и почему. В боевом прогоне не участвует — не читается скриптами, служит базой знаний для человека и для агента, который в следующий раз будет менять этот же модуль.

Граница с `knowledge/` (`.claude/rules/memory-rules.md`) — пересечений не допускается:
- **`knowledge/`** — только бизнес-контекст: площадки, правила рынка, данные и предпочтения владельца. Актуальное состояние, не лог изменений (история — в `git log`, не здесь).
- **`docs/adr/`** — только архитектурные решения по коду самого конвейера: почему стадии выстроены так, а не иначе, отброшенные технические альтернативы. Код-уровень одного конвейера, не бизнес-факты.

Факт о рынке/владельце, найденный в `docs/adr/`, или обоснование архитектуры кода, найденное в `knowledge/` — нарушение границы; при обнаружении переносится в правильную папку, не остаётся на месте.

## 3. Три слоя скилла — канон Anthropic

Источник: инженеры Anthropic, AI Code Summit («4 правила промтинга скиллов» — колода владельца, `Правила md.pdf`). Каждый `SKILL.md`-навык — три слоя, не один промт:

- **Слой 1 — Description.** Когда брать скилл. Claude выбирает скилл по description, не по имени — расплывчатая формулировка не подцепится автоматически, точная активируется сама.
- **Слой 2 — Instructions.** Как выполнить задачу. Пошаговый плейбук, не набор общих слов.
- **Слой 3 — `tools/`.** Чем выполнить задачу. Скрипты, API-обёртки, шаблоны, файлы-референсы — детерминированный код вместо того, чтобы Claude каждый раз заново писал или пересчитывал одно и то же. Это самый недоинвестированный слой на практике — большинство останавливается на 1–2, и именно `tools/` отличает рабочий скилл от красивого промта без реальной силы («People put a lot of effort into beautiful, detailed prompts. And then the tools they make are incredibly bare-bones» — Eric, Anthropic Engineering).

Композиционность: 3–5 фокус-скиллов вместо одного монолита «делает всё». Один скилл — одна зона ответственности, Claude координирует между ними сам. Монолитный скилл ломается непредсказуемо — улучшение одного кейса портит три соседних; фокус-скилл тестируется и улучшается отдельно.

**Оркестраторный `SKILL.md` (тот, что ведёт весь конвейер §5) — не считает сам и не пишет код.** Его роль — дирижёр: запускать стадии по порядку, отдавать команды скриптам, вызывать узких субагентов на развилках, следить за Circuit Breaker (§7) и отдавать человеку итог. Для него слой Description (§3, слой 1) обязан быть исчерпывающим, не общей формулировкой «когда брать»: явно перечислены точные CLI-команды, которые он запускает под капотом (`python3 -m pp.run <stage>`), полный список субагентов, которых он вызывает, и пользовательские фразы-триггеры.

**Закон поверхности оркестратора.** Оркестраторный скилл трогает только четыре вещи: входные данные, промежуточные артефакты в `out/`, архив в `runs/<timestamp>/` и пороги из `config.json`. Любое число мимо этих четырёх источников — то же нарушение, что хардкод порога в модуле (§4), только на уровне самого дирижёра, а не отдельного расчёта.

## 4. `config.json` обязателен — запрет хардкода порогов

Любой численный порог (когда включать платное продвижение, что считать ценовой аномалией, шаг ставки, лимит повторов) выносится в `config.json` проекта. Число, зашитое в код модуля или в текст `SKILL.md`/`CLAUDE.md` вместо ссылки на порог из `config.json` — дефект, не деталь реализации. Порог, заданный словом («если письмо срочное») вместо числа со сравнением — тот же дефект в текстовой форме: ломается на первом граничном случае, который не совпал со словом буквально.

## 5. Архитектура сквозного конвейера — эталонная нумерация (когда применимо, §0)

```
0  validate   (скрипт)  входные данные → data_quality.json
1  audit      АГЕНТ     аудит качества (только спорные позиции)
2-6 расчёт    (скрипты) факты, классификация, прогнозы, распределение
7  triage     (скрипт)  фильтрует аномалии/спорные позиции → пакует в out/exceptions/<kind>-NN.json
8  analyse    АГЕНТЫ    параллельный разбор своих пачек exceptions
9  resolve    АГЕНТ     сведение решений субагентов
10 merge      (скрипт)  слияние расчётов и правок
11 review     АГЕНТ     финальный аудит
12 render     (скрипт)  сборка фида/дашборда
```

**`triage` (7) — реализация принципа «маршрутизация тоже код» (§1) в конкретном коде.** Отдельный скрипт, не часть расчётных модулей 2–6: находит спорные/аномальные позиции по табличным пороговым правилам (пример — 8 типовых ситуаций → 4 адресата, см. §1), пакует их батчами (например `batch_size: 25`) по адресу конкретного профильного субагента в `out/exceptions/<kind>-NN.json`. `analyse` (8) читает только свою пачку — не весь `out/exceptions/`.

Число параллельных `analyse`-субагентов и разделение `analyse`/`resolve` на разные вызовы — не фиксированная часть канона, а функция реального объёма спорных позиций за прогон. При малом объёме `audit`/`analyse`/`resolve` — один и тот же узкий субагент, не три (см. §0, пример Авитолога на 2026-09-09).

**Проверка мусором — обязательный acceptance-тест стадии `0 validate`.** Подать на вход заведомо негодные данные (пустой файл, файл не той структуры, текст вместо числа) и проверить: система отказывается считать, называя причину («в остатках нет августа, считать нельзя»), а не выдаёт уверенный результат на битых данных. Система, которая на мусоре бодро посчитала что-то похожее на правду — не имеет реальной развилки на этой стадии, и однажды так же бодро посчитает на боевых битых данных незаметно для владельца.

## 6. Контракт вывода субагента (бланк) и узкие роли

Свободный текст между двумя субагентами работает, пока звеньев в цепочке два. На третьем звене интерпретация плывёт: второй агент написал абзац своими словами, третий понял его по-своему — и это видно только на самом выходе, когда уже неясно, где именно сломалось. Решение — субагент отвечает не прозой, а по закрытому бланку.

**Обязательные свойства бланка вывода:**
- **Решение — из закрытого списка**, не свободная формулировка. Четвёртого варианта, которого нет в списке, не существует; ответ не по списку — не принимается, а не додумывается.
- **Величина — число**, не «побольше»/«примерно». Если решение требует масштаба (насколько поправить, на сколько сдвинуть) — конкретное число, с которым можно работать дальше без интерпретации.
- **Область действия — явный список**, не «вообще». На какие позиции/периоды/сущности распространяется решение — перечислено, не подразумевается.
- **Причина — из закрытого enum**, не произвольное объяснение. Заранее заданный словарь типовых причин (по образцу «настоящий рост / сезон / отложенный спрос / раздуто акцией / случайность» — словарь свой под задачу, принцип общий).
- **Уверенность — явный уровень** (высокая/средняя/низкая). Низкая уверенность — не повод додумать самому, а автоматический эскалационный триггер: позиция уходит человеку, не проходит дальше по цепочке как обычный ответ.
- **Свободного поля «на подумать» в бланке нет.** Всё, что не влезло в закрытые поля, дальше по цепочке не идёт — это осознанное ограничение, а не недосмотр в дизайне бланка.

**Закрытый словарь — не только в тексте инструкции, но и продублирован в коде рядом с местом вызова агента** (например, константа `FORM` в модуле, который формирует запрос к модели) — чтобы ответ агента можно было сверить программно, не только напомнить словами в промпте. Одна и та же декларация значений в двух местах (рядом с бизнес-логикой и рядом с вызовом LLM) — не дублирование ради дублирования, а механическая проверка вместо надежды, что модель помнит список.

**Проверка бланка — часть конвейера, не факультатив.** Ответ агента сверяется с бланком по форме сразу на выходе, не через несколько шагов, когда уже непонятно, кто виноват. Не прошёл проверку — переспросить ещё раз тем же вопросом; снова мимо — позиция помечается «решает человек», не пропускается на следующую стадию с натяжкой.

**Узкая роль проверяется тестом «не делает: …».** У каждого субагента/скилла в описании обязана быть строка, что он НЕ делает — не менее важная, чем то, что делает. Не получается сформулировать «не делает: …» одной внятной фразой — роль слишком широкая, дели надвое. Признак переразмытой роли текстом: слово «и» в описании обязанностей встречается больше двух раз («смотрит спрос и поставки и считает объём и пишет отчёт») — такая роль хуже трёх узких, потому что у неё нет проверяемого критерия успеха.

**Вход субагента — минимальная выжимка, не доступ к сырым данным.** Субагенту передаётся ровно тот минимум, на котором можно принять решение (например: продажи по месяцам, остаток, наценка по одной позиции) — не ссылка на полную выгрузку и не «пусть сам найдёт нужное». «Дать побольше на всякий случай» — то же самое переразмытие входа, что и переразмытая роль: субагент топит важное в объёме и начинает терять середину. Это требование того же типа, что «строго объявленные tools» в декларации субагента (§1) — только применённое не к правам на инструменты, а к объёму данных на входе.

## 7. Архитектурные границы и изоляция

- **Изоляция модулей на уровне импортов.** Модули стадий друг о друге не знают и не импортируют друг друга напрямую — максимум общую конфигурацию и общий ввод-вывод (`config`/`io`). Стыковку между стадиями делает только сам оркестратор (`pipeline.py`). Прямой импорт одной стадией другой — тот же архитектурный дефект, что и «два владельца одного порога» ниже, просто на уровне кода, не решения.
- **Ровно два шва для тестов, новых не заводить.** Один сквозной (`pipeline.run(stage, config)` — весь конвейер целиком) и один чистый (главная функция ядра без побочных эффектов, например `plan_sku(facts, forecast, cfg)`). Остальные модули тестируются через эти два шва, не получают собственной параллельной тестовой инфраструктуры — иначе тестовый код начинает дублировать сам конвейер.
- **Одно решение — один владелец.** Модуль/агент A владеет группой расчёта и её объёмом; модуль B имеет право читать вывод A, но не пересчитывать его пороги заново. Два владельца одного решения — архитектурный дефект, не гибкость.
- **Порядок старшинства при конфликте решений задаётся один раз, заранее, статично.** Когда по одной сущности легитимно высказались два разных владельца (например: решение «эту позицию вообще не заказывать» и решение «сколько заказывать») — заранее прописанный приоритет одного решения над другим, не «кто ответил первым» и не разбор на лету. Без статичного порядка система на одних и тех же данных отвечает по-разному в зависимости от порядка выполнения — это дефект воспроизводимости, а не гибкость логики.
- **Circuit Breaker — два разных отказа, два разных ответа, не путать.**
  - **Hard Stop (фатальная ошибка входа/валидации, стадия `0`).** Данные испорчены целиком или структурно не годятся — конвейер останавливается немедленно, до запуска любых LLM-субагентов дальше по цепочке. Ноль сожжённых токенов на заведомо мусорном прогоне — это и есть предмет «проверки мусором» из §5.
  - **Soft Flag (отказ отдельного субагента на одной позиции, стадии `1`/`8`/`9`/`11`).** Субагент отказал, не смог решить или не прошёл проверку бланка (§6) — конвейер не падает: позиция получает статус `needs_human_review`, остальные строки продолжают детерминированно считаться и доходят до `render` как обычно. Единичный отказ — состояние одной строки, не авария всего прогона.
  - Спутать эти два случая — значит либо останавливать весь прогон из-за одной спорной позиции (Hard Stop там, где нужен Soft Flag), либо тихо досчитывать что-то на заведомо битом входе (Soft Flag там, где нужен Hard Stop). Оба — архитектурный дефект, не вариативность поведения.

## 8. Gotchas — куда обязательно смотреть при сборке под этот стандарт

- Жизненный цикл staging/commit: какой прогон черновой, какой фиксируется как боевой — прописать явно в паспорте, не полагаться на память агента.
- **Публикация результата — атомарная ротация `out/` → `runs/<timestamp>/`, конкретный механизм.** Прогон пишет не сразу в боевой `out/`, а в `out.staging/`; внутри самого прогона чтение промежуточных артефактов видит только staging, без тихого отката к данным прошлого `out/` (иначе пропущенная стадия незаметно скормит следующей прошлогодние числа). Только по завершении — один атомарный `os.rename`: `out.staging/` становится новым `out/`, прежний `out/` уезжает в `runs/<timestamp>/`. Любой обрыв на середине прогона — `out/` остаётся прежним, целым; в `runs/` ничего не появляется до успешного завершения. Это даёт полную воспроизводимость: любой прошлый прогон можно открыть и сравнить с текущим цифра к цифре.
- `runs/<date>/` — архив прошлых прогонов, задним числом не трогать.
- **Не каждый артефакт участвует в атомарной ротации — есть именованное исключение.** Отчёты, которые должны пережить даже фатально оборвавшийся прогон (например, отчёт о качестве входных данных — нужен ревьюеру, даже если сам прогон встал на стадии `0`) или пережить следующий прогон целиком (история точности прогнозов — иначе доказательство теряется сразу после получения) — пишутся отдельно от staging-механизма, не участвуют в общем `os.rename`. Список таких файлов зафиксирован явно и один раз (например, `UNSTAGED_ARTIFACTS` в модуле ввода-вывода), не разбросан по коду молчаливыми исключениями.
- **Стадия пропускается только по одному, явному критерию — отсутствию своего файла в ядре.** Модуль стадии физически не существует → штатный пропуск, отражается в журнале прогона как ожидаемое. Модуль существует, но не хватает нужной функции внутри, либо он падает `ImportError` — это ошибка конвейера, а не пропуск; путать эти два случая означает тихо терять стадию, которая должна была отработать.
- **Каждый модуль ядра начинается докстрокой «что здесь спрятано» одной-двумя строками** — не описание того, что и так видно из имени функций, а неочевидный контекст (почему стадия считает именно так, какая развилка внутри). Обновляется вместе с правкой кода того же модуля, не отдельным проходом позже — иначе докстрока начинает врать раньше, чем кто-то это заметит.
- Пустые/пропущенные значения — не ноль по умолчанию; `None` с зафиксированной причиной пропуска, иначе агент на следующей стадии примет молчаливый ноль за реальный факт.
- **Журнал прогона фиксирует минимум:** когда и сколько шёл прогон (аномальная длительность — первый сигнал, что что-то изменилось); какие стадии отработали, какие пропущены (пусто в «пропущено» — хороший знак, первое место, куда смотрят при странном результате); какие роли/субагенты реально участвовали; снимок всех порогов `config.json` именно на момент этого прогона — без снимка причину расхождения результатов между прогонами через месяц не найти никогда, если кто-то тихо поменял порог.

## 9. Порядок сборки нового агента

1. **Каркас Foundation** — развернуть только на чистом скелете (`CLAUDE.md`, `.claude/rules/`, `.claude/skills/`).
2. **Комплектация** — подобрать строго 3–5 целевых навыков из `Skill System` под специализацию агента, с обоснованием каждого.
3. **Запрет на раздувание (No Bloatware)** — не создавать самовольно папки вроде `knowledge/`, файлы сессионной памяти, не размывать системный промпт.

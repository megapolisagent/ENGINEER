# legacy-repository-audit
## Проверка старого/внешнего репозитория перед тем, как строить новое

> Собрано 2026-08-13, пока не в Skill System — рабочая калька конкретно для Engineer, не оформленная общая методика. Проверяется на следующем реальном аудите; усиливается дальше только если снова что-то пропущено, не заранее.

## Главный принцип

**Исследование источника ≠ выбор того, что забрать.** Правильный цикл, без исключений:

```
исследовала → полный инвентарь фактов (в файле) → для каждой строки
проверила, нет ли уже у нас → классифицировала → показала владельцу
целиком → владелец решил → только теперь внедрила
```

## Когда нанимают

Владелец называет конкретный старый/внешний репозиторий агента и просит проверить его — обычно перед тем, как строить новых агентов, чтобы не переизобретать то, что уже сделано или уже решено не делать.

## Когда нельзя использовать

- Разбор текущего, живого репозитория самого Engineer/Researcher — для этого есть `architecture-review`/`repository-design`, не этот Skill.
- Ревью кода перед доставкой — не про это.
- Задача не про целый репозиторий, а про один конкретный файл/вопрос — избыточно, читай файл напрямую.

## Входные данные

- Ссылка на репозиторий (обычно GitHub).
- Что уже известно о его происхождении, если что-то известно (не выдумывать, если неизвестно).

## Метод

### Шаг 1 — Безопасная read-only копия, не обязательно клон
Создать безопасную read-only рабочую копию или использовать другой безопасный способ полного чтения (например, прямое чтение файлов через GitHub без полного клонирования, если этого достаточно для задачи) — не клонировать механически каждый раз, если способ легче даёт тот же результат. Оригинал не изменять в любом случае. Если всё же клонируешь — объяснить владельцу, что это значит, при первом упоминании в разговоре, не просто назвать действие.

### Шаг 2 — Идентификация, отдельным сообщением, до глубокого чтения
Прочитать только входные/навигационные файлы (README/CLAUDE.md/дашборд/входная точка). Ответить на три вопроса и показать владельцу **до** перехода к Шагу 3:
- Что это за агент/система?
- За что она отвечает?
- Как она связана с текущей системой — предшественник, замена, что-то отдельное, всё ещё живая или остановленная? Если неизвестно — спросить владельца прямо, не предполагать.

### Шаг 3 — Чтение по одинаковым категориям, глубина — по материалу, не механически
Проверить все девять категорий ниже без исключения. Если категории нет в этом репозитории — явно отметить «не обнаружено», не пропустить молча. Но **глубина** чтения внутри каждой категории определяется тем, есть ли там материал и насколько он потенциально ценен — не читать раздел MCP с той же дотошностью в чисто маркетинговом репозитории, где MCP просто нет, что и в инженерном.

1. **Архитектура и принципы** — на чём построен репозиторий, какие правила заявляет сам о себе.
2. **Skills** — воспроизводимые методики, независимо от домена.
3. **MCP / инструменты** — что подключено, что заявлено, но не подтверждено реально работающим.
4. **Модели и роутинг между ними** — какая модель для какой задачи, по какому правилу, учёт стоимости/юрисдикции данных.
5. **Агенты / специализации** — конкретные построенные экземпляры, их роли, статус.
6. **Методологии** — предметные профессиональные методы (Craft).
7. **Правила и принципы работы** — как система принимает решения, эскалирует, останавливается.
8. **Архитектурные механизмы** — lifecycle, permissions, registry, memory-модель, review/validation.
9. **Собственная история решений и самопроверок** (decisions/changelog/retrospective) — самый ценный материал, если есть.

### Шаг 4 — Инвентарь фактов, в файл, без единой оценки
Записать в файл `workspace/<дата>-legacy-audit-<имя-репозитория>.md` **чистую таблицу фактов**, без малейшей классификации или решения — это только фиксация того, что реально увидела:

| Что найдено | Где найдено (файл/раздел) | Краткое содержание | Доказательство | Статус доказанности |
|---|---|---|---|---|
| … | … | … | цитата/ссылка на конкретное место | реально использовалось / проверено, но не в проде / только описано / неизвестно |

**Статус доказанности** — отдельная, обязательная колонка: не путать красиво описанную методику или Skill с тем, что реально прошло проверку практикой. Задумка, правило, архитектурная схема и реально работающий, использованный механизм — не один уровень доверия, разница обязана быть видна в таблице, не только в голове.

### Шаг 5 — Классификация, отдельным проходом, после инвентаря
Только теперь, по каждой строке из Шага 4, отдельная таблица:

| Что это (категория из Шага 3) | Уже есть у нас? | Куда положить | Забираем? | Почему |
|---|---|---|---|---|
| Skill / MCP / модель / агент / методология / правило / механизм | да / нет / не проверено | Skill System / Дом / Engineer / владелец сам | да / нет / UNKNOWN | … |

«Уже есть у нас?» — реальная проверка по `registry.json`/`HOME.md`/файлам напрямую, не по памяти разговора и не по догадке из категории находки, для каждой строки без исключений.

### Шаг 6 — Не путать «не нашла» с «этого нет»
Если находка упомянута в самом репозитории (ссылка, пункт реестра), но физически не найдена в прочитанной копии — статус находки в Шаге 4 — **«не нашла в этой копии»**, не «в репозитории этого нет». Указать, где искала.

### Шаг 7 — Не путать интерпретацию с фактом
Каждое утверждение о содержимом репозитория в таблицах Шагов 4-5 — либо факт с указанием конкретного места (колонка «Доказательство»), либо явно помеченный вывод/предположение Engineer. Тот же принцип ЗНАЮ/ПРЕДПОЛАГАЮ/НЕ ЗНАЮ, применённый к чтению чужого репозитория.

### Шаг 8 — Внешние факты, на которые ссылается сам репозиторий — проверять
Если находка ссылается на внешний источник — проверить напрямую (`WebFetch`/`WebSearch`) или через Researcher. Не выдавать чужую цитату за подтверждённый факт без проверки.

### Шаг 9 — Итоговый отчёт, фиксированная структура, дождаться решения владельца

```
1. ИДЕНТИФИКАЦИЯ (Шаг 2)
2. ИНВЕНТАРЬ ФАКТОВ (Шаг 4) — вся таблица, включая статус доказанности
3. КЛАССИФИКАЦИЯ (Шаг 5) — вся таблица, включая UNKNOWN
4. ЧТО РЕШЕНО НЕ БРАТЬ — отдельно, с причиной каждого пункта
5. ЧТО НЕ НАЙДЕНО (не то же самое, что «этого нет»)
6. ЧТО ОСТАЁТСЯ НЕИЗВЕСТНЫМ
```

Ничего не внедряется до подтверждения владельца по каждой строке.

### Шаг 10 — Исполнение только после подтверждения, по файлу
Открыть файл из Шага 4 заново и вычёркивать строки по нему, не по памяти разговора.

## Self Check («И что с того?»)

Если владелец после отчёта спросит «а что ещё не взяли и почему» — есть ли готовый, полный ответ без необходимости заново перечитывать репозиторий? Если нет — Шаг 4 не был доведён до конца.

Если Engineer поймала себя на фразе «я решила не брать X» до того, как владелец увидел X в отчёте, — нарушение главного принципа.

## Checklist

- [ ] Read-only копия или безопасное прямое чтение — оригинал не тронут
- [ ] Идентификация показана владельцу отдельно, до глубокого чтения
- [ ] Прочитано по всем девяти категориям, отсутствие явно помечено; глубина — по материалу, не механически одинаковая
- [ ] Инвентарь фактов (Шаг 4) записан в файл без единой оценки/классификации, включая статус доказанности
- [ ] Классификация (Шаг 5) — отдельным, более поздним проходом, не смешана с инвентарём
- [ ] «Уже есть у нас?» проверено реально для каждой строки
- [ ] «Не нашла» и «этого нет» различены явно
- [ ] Факты и собственные выводы Engineer разделены явно
- [ ] «Забираем?» — да/нет/UNKNOWN для каждой строки
- [ ] Внешние ссылки проверены, не принята чужая цитата без проверки
- [ ] Итоговый отчёт — по фиксированной структуре Шага 9
- [ ] Решение «забираем» по каждой строке — слово владельца
- [ ] Исполнение вычёркивается по файлу, не по памяти

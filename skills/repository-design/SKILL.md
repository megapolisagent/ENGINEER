# Repository Design

## Principle

Собрать репозиторий агента — не значит изобрести структуру заново. Значит найти в уже готовом фундаменте (Foundation) точки расширения и правильно их заполнить, не трогая то, что фундамент уже решил сам. Любой репозиторий профессионального агента отвечает на один и тот же список вопросов — независимо от того, чем именно фундамент реализован сегодня:

1. Где документ, объясняющий, зачем агент существует?
2. Где устав — кто агент и как он работает?
3. Где характер/тон, специфичный для этой специализации?
4. Где профиль владельца, для которого работает агент?
5. Где память, которая верна всегда, и где — то, что меняется от сессии к сессии?
6. Где накопленные знания по темам, читаемые точечно под задачу?
7. Где переносимые способности (Skills) и как они устанавливаются?
8. Где агент оставляет результаты своей работы?
9. Где решается, что читать под конкретную задачу?
10. Как агент обновляется, не теряя личных/накопленных данных?
11. Где фиксируется история решений и их статус?
12. Где живут вопросы, на которые ещё нет ответа?

Если репозиторий не даёт ответа на один из этих вопросов явным файлом — это дыра в дизайне, а не мелочь.

## Implementation (в этом проекте — Foundation)

| Вопрос | Файл/папка Foundation | Кто заполняет |
|---|---|---|
| 1. Зачем существует | `VISION.md` | Foundation (не трогать) |
| 2. Устав | `HOME.md` | Foundation задаёт форму; специализация вписывает роль в раздел «Кто ты» |
| 3. Характер | `SOUL.md` | Специализация (точка расширения, пуст в Foundation) |
| 4. Профиль владельца | `PROFILE.md` | Заполняется по ходу знакомства с владельцем — не выдумывать заранее |
| 5. Память: устойчивая / по сессиям | `MEMORY.md` / `memory/` | Foundation задаёт механизм; агент пишет в него по ходу работы |
| 6. Знания по темам | `knowledge/` | Агент пишет по ходу работы |
| 7. Способности | `skills/` (рабочий стол) + Skill System (внешний источник) + скилл `installer` | Устанавливаются только через `installer`, не пишутся вручную в тело агента |
| 8. Результаты работы | `workspace/` | Пустой каркас на старте, агент кладёт результаты по ходу |
| 9. Что читать под задачу | `ROUTING.md` | Foundation задаёт таблицу потребностей; специализация дописывает свои строки в раздел knowledge-роутинга |
| 10. Безопасное обновление | `UPDATE.md` + `update.sh` | Foundation (не трогать) |
| 11. История решений | `DECISIONS.md` | Foundation задаёт формат (Proposal → Discussion → Locked); агент пишет записи по ходу |
| 12. Открытые вопросы | `OPEN_QUESTIONS.md` | Агент пишет по ходу |

Источник таблицы: `Foundation/03_ARCHITECTURE/FOUNDATION_ARCHITECTURE.md` и `Foundation/04_REPOSITORY/README.md` — внутренние документы этого же проекта, не внешний материал, лицензионных ограничений нет.

## Что специализация никогда не трогает

`VISION.md`, `AGENTS.md`, `UPDATE.md`, `update.sh`, механика `ROUTING.md` (можно дописывать строки под свои knowledge-файлы, нельзя менять правило «не смешивать меню и триггер-фразы») — это принадлежит Foundation. Правка этих файлов агентом без явного решения владельца — нарушение, см. `Foundation/04_REPOSITORY/DECISIONS.md`.

## Output Contract и Few-shot — не для каждого агента, а по типу результата

Применимо только к агентам, чей результат — текстовый ответ, который владелец читает и оценивает (аналитик, консультант, юрист, маркетолог). Не применимо к агентам, чей результат — артефакт вне текста ответа (сгенерированный файл, код, программный движок вроде `AI Legal Constructor`) — там формат задаёт сам артефакт, не разговорный контракт.

### Output Contract — фиксированная структура ответа

Если специализация регулярно выдаёт содержательный вывод (не короткий факт, не техническое подтверждение) — `SOUL.md` фиксирует обязательную структуру этого вывода: какие разделы обязаны быть в каждом содержательном ответе, в каком порядке, что в каждом разделе. Отсутствующий раздел — дыра в контракте, не стилистическое расхождение.

Что не делать: не копировать единый шаблон разделов на все специализации (внешний материал предлагает «Квалификация / Анализ рисков / Решение / Документ» — это для юридического/риск-домена, не универсально). Разделы определяет сама специализация под свою профессию, не Foundation.

### Few-shot — образцовый диалог, не описание стиля

Если словесное описание «Характера»/«Запретов стиля» на практике не удерживает результат в нужных рамках (расхождение поймано владельцем постфактум, не на сборке) — добавь в `SOUL.md` один короткий образцовый пример: реалистичный вход → эталонный по формату и тону выход. Не иллюстрация вообще, а конкретный кейс, максимально похожий на настоящую задачу специализации.

Не по умолчанию: пример нужен, только если словесного описания оказалось недостаточно на практике — не пиши заранее «на всякий случай», это дублирование одного факта в двух формах без причины.

## Data Contract и запрет ad-hoc генерации документов

Внесено по итогам независимого аудита Codex (`workspace/2026-09-02-задача-стандарт-data-contract-и-e2e-приёмка.md`) — до этого правила не существовало вообще: выбор подхода к обмену данными и генерации документов решался ситуативно на каждой сборке, а не по единому стандарту. Сам аудит нашёл в этом встроенное противоречие: протокол проверки через Codex (`instructions/codex_deep_audit_prompt.md`) уже требует проверять «синхронность с API и схемами», но сборка агента нигде не была обязана эти схемы создавать.

**Data Contract — обязателен до бизнес-логики.** Если агент обменивается структурированными данными с файлом, другим агентом или внешним API — прежде чем писать код, который эти данные обрабатывает, зафиксировать явную схему: минимум — Pydantic-модель, максимум — строгая JSON Schema, с явным перечнем обязательных полей и типов. Схема живёт рядом с кодом (например, `models.py` уже используется в `AI Legal Constructor` — доводим до полноценной модели с валидацией, не оставляем внутренним соглашением без проверки на входе). Код, который читает данные без проверки через эту схему (просто `json.loads(...)` и работа с словарём) — не считается готовым.

**Запрет ad-hoc скриптинга генерации документов.** Генерация структурированных документов (`.docx`, `.xml`-фиды и подобные) не пишется точечной заменой текста/поиском по фрагменту — это класс ошибок, реально случившийся на практике (перекрёстные ссылки в договоре ломались молча при каждой правке, `AI Legal Constructor`, реальный кейс 2026-09-02). Обязателен промышленный шаблонизатор с явными метками (`docxtpl`/Jinja2 — `{{ variable }}`, не ручной поиск строки в XML `.docx` или построчная замена в тексте). Правило распространяется на новые сборки и на доработку существующих генераторов документов при следующей значимой правке — не требует немедленного рефакторинга всего, что уже работает, если оно не трогается прямо сейчас.

## Behavioral & Communication Contract

Внесено по итогам разбора владельцем реального инцидента (`AI Legal Constructor`, сделка аренды 2026-09-02, `workspace/2026-09-02-задача-behavioral-craft-standard.md`) — технических контрактов (схема данных, шаблонизатор) недостаточно, если сама роль спроектирована как «слепой исполнитель», а не консультант, защищающий интересы доверителя. Применимо к любому агенту, который консультирует владельца/клиента или готовит для него документ/решение с реальной ценой ошибки — не применимо к чисто техническим/инфраструктурным агентам без роли консультанта.

**Advisory First.** Запрещено генерировать документ/артефакт по «сырому» запросу без предварительного скрининга рисков и статуса сторон, относящихся к предмету запроса (для юриста/консультанта — налоговые последствия, полномочия по доверенности, регуляторные требования к сроку/форме). Скрининг — короткий, по существу, до начала сборки документа, не после: «прежде чем собрать договор, вот что важно про вашу ситуацию — X, Y».

**Clarification Protocol (Socratic Gate).** Если во входных данных нет существенного условия — агент обязан остановиться и задать структурированный вопрос, не подставлять правдоподобное значение по умолчанию. Додумывание конкретных чисел/условий (дата платежа, лимит, сторона договора) вместо вопроса — нарушение этого протокола, не мелкая неточность.

**Doubt Protocol — презумпция неполноты данных.** При работе с нечётким сканом/фото/файлом запрещён категоричный вывод об отсутствии права или факта на основании беглого/неуверенного прочтения. Формулировка при неуверенности: «на этом фрагменте не удаётся разобрать X, пришлите более чёткую копию/уточните Y» — не «права нет» или «документ не подтверждает». Реальный сбой, из-за которого правило внесено: беглое чтение доверенности привело к ошибочному выводу «нет права сдавать в наём», хотя при внимательном чтении право было прямо прописано — вывод чуть не отправил владельца оформлять доверенность заново через консульство.

**Tone of Voice — партнёрский голос.** Запрет на сухие системные отписки, самооправдания за счёт третьей стороны («это не я, это сайт-донор/Росреестр виноват») и перекладывание сверки результата на пользователя («проверьте сами»). Агент, выполняющий консультативную роль, говорит как внимательный ведущий специалист, который сам держит ответственность за качество своего результата — тон фиксируется в `SOUL.md` специализации (см. «Output Contract и Few-shot» выше — тот же механизм фиксации тона, применённый к этому конкретному классу провала).

## Tooling Inventory

Внесено по итогам контрольного аудита Codex (2026-09-02, `workspace/2026-09-02-задача-tooling-inventory-и-закрытие-аудита.md`) — после явно отклонённой более узкой формулировки «обязательный `.mcp.json` для каждого агента». Отклонено технически: MCP — протокол для подключения внешнего сервиса, которого у Claude Code нет по умолчанию; файловая система и веб уже встроены в каждую сессию (`Read`/`Write`/`Bash`/`WebFetch`/`WebSearch`), а Python-библиотека вроде `docxtpl` подключается через `import`, не через MCP. Требование MCP-конфига там, где он не нужен, создало бы фиктивную инфраструктуру ради галочки — тот же класс ошибки, что и запрет ad-hoc скриптинга выше, только в обратную сторону. Применяется принцип `instructions/capability-resolver.md` — потребность отдельно от инструмента.

**Фиксация реального класса инструмента.** Для каждой операции, которой агент читает вход или отдаёт результат вовне (файл, API, документ, поиск) — явно назвать, чем это физически делается: штатный инструмент среды Claude Code (`Bash`/`Read`/`Write`/`WebFetch`/`WebSearch`), Python-библиотека (зафиксирована в `requirements.txt`, если она есть у агента), собственный скрипт автоматизации, или внешний MCP-сервер — MCP выбирается только тогда, когда ни один из первых трёх классов задачу не закрывает, тем же резолвингом, что уже описан в `capability-resolver.md`.

**Критерий сдачи — реальный прогон, не декларация.** Инструментальная цепочка считается готовой не потому, что она описана в промпте/инструкции, а потому, что был выполнен настоящий вызов на реальных данных с наблюдаемым результатом (тот же принцип, что уже требует чек-лист «агент готов к реальной работе» для Working Loop в целом — здесь применяется отдельно к каждому классу инструмента, не только к сценарию целиком).

## Правило README и профессиональных надстроек

Найдено на трёх реальных проходах в одной сессии: (1) README Engineer открывался собственной архитектурной схемой — плохо; (2) исправление получилось коротким, но вместе со схемой выкинуло почти весь настоящий объём — тоже плохо, другая ошибка того же ремонта; (3) построчный разбор реального рыночного README (`nick-vels/skills`, 18 разделов, ни одного лишнего) показал, каким должен быть настоящий объём. Краткость и архитектурность — два разных недостатка, лечатся по-разному, нельзя чинить один и получить в подарок другой.

### Порядок содержания — приоритет, не жёсткий шаблон

1. **Одна сильная строка обещания** — что получает владелец, не как это устроено.
2. Короткое объяснение: что это, чего не нужно делать самому.
3. **Если у агента есть что показать во время или после работы** (визуальный результат, отчёт, дашборд) — показать здесь, как доказательство, раньше раздела про установку/использование, не в конце как приложение.
4. **Как этим пользоваться — через настоящий, конкретный пример** задачи/запроса, не через абстрактную категорию («у вас есть режимы поиска/файлов/трекинга» — плохо; «/задача: телеграм-бот, который принимает заявки и складывает в таблицу» — хорошо).
5. Если есть режимы/настройки работы — что переключает, что не меняется никогда ни в одном режиме.
6. **Механизмы доверия — конкретно**, не декларативно: не «мы проверяем качество», а как именно (например: отдельный агент без доступа к промежуточным документам сверяет результат с исходным текстом владельца, не с пересказом).
7. Явные границы: когда использовать, когда нет — честно называть случаи, где агент не подходит.
8. **Если агент имеет дело с чувствительным** (ключи, доступы, деньги, персональные данные) — отдельный явный раздел: что никогда не запросят, что произойдёт, если владелец всё равно передаст такое.
9. Что агент никогда не делает — короткий список жёстких границ, отдельно от «когда не подходит».
10. Практическая эксплуатация — обновление/удаление/что делать, если что-то ведёт себя не так, если это применимо к этому агенту.
11. **Техническая структура репозитория — обязательный раздел, самым последним перед мета** (не «если нужно глубже», а всегда): дерево профессионально значимых папок (`skills/`, `knowledge/`, `workspace/`, аналоги у другого агента) с короткими пояснениями напротив каждого пункта, не сплошной прозой — одна строка закрытия про формат (обычный markdown, можно открыть и прочитать конкретный файл).
12. Лицензия / мета — в самом конце.

### Визуальное качество, не только состав

Там, где содержание структурное (режимы, when/when-not, дерево файлов) — таблица или дерево с подписями читается лучше сплошного абзаца (подтверждено `nick-vels/skills`: таблицы для режимов, глубины, «когда не подходит»; дерево с инлайн-комментариями для структуры). Проза — для объяснения поведения и примеров, не для перечислений.

### Что не копировать механически

Не каждому агенту нужны все 12 пунктов — пункт появляется, потому что у **этого конкретного** агента есть соответствующее реальное поведение (дашборд — только если он правда есть; раздел про ключи — только если агент правда имеет дело с чувствительным), не по привычке или ради полноты списка.

### Различать обязательное ядро Foundation от надстройки профессии

12 строк таблицы Implementation выше — у любого агента. Надстройка, специфичная для профессии конкретного агента (глубокий процессный документ вроде `LIFECYCLE.md`, дополнительные Skills, дополнительные файлы `knowledge/`) — оправдана, только если сама профессия её требует, не потому что предыдущая сборка (например, сам Engineer) её имела. Тест перед добавлением файла сверх 12 строк: «Foundation требует / профессия требует / скопировано по привычке?» — третий ответ не считается причиной. Тот же тест применяется и к новому top-level разделу самого `HOME.md` (не только к отдельным файлам) — см. чек-лист «репозиторий готов» ниже.

### Финальная проверка перед тем, как считать README готовым

Раздельно, не одним вопросом: (а) нет ли архитектурной схемы/внутреннего пайплайна как первого экрана? (б) не выхолощен ли вместе с ней настоящий объём — конкретные примеры, границы, механизмы доверия? README, прошедший только проверку (а), но не (б), не готов.

## Чек-лист «репозиторий готов»

- ☐ `VISION.md`, `AGENTS.md` на месте, не изменены относительно Foundation. `HOME.md` на месте: структура Foundation HOME должна сохраняться. Раздел «Кто ты» — точка расширения специализации без ограничений (строка 2 таблицы Implementation выше). Новый top-level раздел сверх структуры Foundation допустим, только если его ответственность действительно принадлежит специализации, не может быть выражена существующей точкой расширения и необходима для рабочего контракта агента — тот же тест «Foundation / специализация / локальная привычка», что и для отдельных файлов ниже, не самопровозглашённое расширение.
- ☐ `SOUL.md` заполнен специализацией (не пустой шаблон-заглушка).
- ☐ Если специализация выдаёт содержательный текстовый вывод для владельца — `SOUL.md` фиксирует Output Contract (обязательные разделы ответа) и, если словесного описания стиля оказалось недостаточно на практике, короткий few-shot пример. Не применимо, если результат агента — не текст ответа, а отдельный артефакт.
- ☐ **Если агент консультирует владельца/клиента или готовит документ/решение с реальной ценой ошибки** — `HOME.md`/`SOUL.md` фиксируют Behavioral & Communication Contract (Advisory First, Clarification Protocol, Doubt Protocol, Tone of Voice — см. раздел выше), не только Output Contract по форме ответа.
- ☐ **Tooling Inventory зафиксирован** (см. раздел выше) — для каждой операции с внешним
  вводом/выводом назван реальный класс инструмента (штатный тул / Python-библиотека /
  скрипт / MCP при подтверждённой необходимости), и цепочка проверена реальным прогоном,
  не только описана в инструкции.
- ☐ `PROFILE.md` либо честно пуст (агент ещё не знаком с владельцем), либо заполнен из реального интервью — не выдуман.
- ☐ Правила Engineer об общении с этим конкретным владельцем, уже известные из собственной памяти Engineer (`ENGINEER/MEMORY.md`, `ENGINEER/memory/`) — выписаны построчно и явно перенесены (или явно отклонены с причиной) в `SOUL.md` нового агента, не молча предполагаются унаследованными.

Новому агенту с пустым `DECISIONS.md` заводить `DECISIONS_ARCHIVE.md` заранее не нужно — файл появляется тем же скриптом, когда порог реально достигнут, не раньше.

Каждый файл сверх 12 строк Implementation прошёл тест «Foundation / профессия / привычка».

## Чек-лист «агент готов к реальной работе», не только «репозиторий собран»

Усиливает последние два пункта чек-листа выше, не заменяет их. Прохождение чек-листа «репозиторий готов» означает, что файлы на месте; этот раздел проверяет агента как работающую систему, прежде чем считать сборку завершённой:

- ☐ **Working Loop подтверждён на реальных данных хотя бы раз** — вход→обработка→выход пройден не гипотетически, а на настоящей задаче специализации. **«Реальные данные» определено буквально (Codex, 2026-09-02): данные, переданные владельцем из живого контекста конкретной задачи — не файл-пример из `examples/` или другой тестовый шаблон, придуманный для проверки.** Прогон на тестовом файле — валидная RED-проверка («движок вообще работает»), но сам по себе не закрывает этот пункт.
- ☐ **Приёмка на «грязном» реальном кейсе, не на чистом идеальном примере.** Хотя бы один прогон Working Loop сделан на кейсе со всеми реальными шероховатостями (не все поля есть, есть сканы/фото документов вместо чистого текста, условия нестандартные — не учебный пример) — агент обязан остановиться и задать конкретные вопросы через явный опросник/интервью, а не подставить собственную оценку вместо пропуска. Молчаливое заполнение пропуска правдоподобным числом — провал этого пункта, не мелкое отклонение (реальный сбой, из-за которого правило внесено — `AI Legal Constructor`, сделка аренды 2026-09-02: день платежа, лимит расхода воды и сторона агентского договора были подставлены агентом самостоятельно вместо вопроса).
- ☐ **Повторяемость** — тот же запуск повторно даёт результат сравнимого качества, не разовая удача первого прогона.
- ☐ **Explainability, если применимо** — если агент фильтрует/оценивает/ранжирует/принимает решения, можно объяснить, почему получен именно такой результат, а не чёрный ящик (сходится с Deterministic/AI границей из Reliability Architecture выше — не отдельная новая проверка, применение того же принципа к готовому результату).
- ☐ **Обратная связь есть** — существует способ узнать, что конкретный результат оказался плохим, и на основании этого поправить (Skill/инструкцию/данные) — не только «работает один раз и всё», хотя бы минимальный, ручной способ.
- ☐ **Если применима Reliability Architecture** (client-facing/decision-making/аналитика/financial) — детерминированная база стабильна и проверена, прежде чем AI-слой поверх неё считается готовым; AI-слой без стабильной базы под собой не считается завершённым.
- ☐ **Связь с Researcher (или другим сиблинг-агентом с накопительной базой) — явное решение, не молчаливый пропуск.** Если у собранного агента есть родственный Researcher-агент в экосистеме — решение «подключаем / не подключаем на v1» записано в `DECISIONS.md`/`OPEN_QUESTIONS.md` этого агента, не просто отсутствует в коде.
- ☐ **Модель под суждение агента — проверяема, не только под узкую Reviewer-проверку.** Тот же повод. Если для Reviewer модель явно зафиксирована (`model: haiku` и т.п.), а для собственного стратегического суждения агента (Approval Gate-уровня решения) — нет фиксации и нет способа проверить, на чём реально идёт сессия, это дыра: узкая слепая проверка выдержит слабую модель, само суждение — нет.
- ☐ **Calibration Log Reviewer'а содержит реальные прогоны, не только запись о создании.** Тот же повод — `reviewer_calibration_log.md` состоял из одной строки «создание, правок не было», хотя Reviewer уже реально вызывался и что-то поймал (Positioning v1) — этот вызов нигде не был виден отдельно от футера самого артефакта. Каждый реальный вызов Reviewer'а на значимом решении — отдельная запись здесь (TASK/CRITERION/RESULT/вывод), не только вердикт в одну строку внутри чужого файла.

Источник: `ai_engineering_operating_system_master.md` старого MAIN_ENGINEER (6 gates: API Reality → Working Loop → Stability → Explainability → Calibration → AI Readiness), переформулировано в терминах уже существующих понятий Engineer, не скопировано как чужая терминология. Внешне не проверялось отдельно — это не рыночный стандарт, а перевод чужого рабочего чек-листа на свой язык, честно назван так.

## Если результат слабый — куда искать причину

Не гадать. Проверять по порядку (источник — `CAPABILITY_MAP.md` Researcher, Capability 3/6/11):

1. Агент заново делает одну и ту же процедурную работу вместо готового метода → не хватает Skill.
2. Агент забывает или противоречит сам себе между сессиями → неверно выбран уровень памяти либо конфликт источников не разрешён (`instructions/memory-rules.md`, «Когда источники расходятся»).
3. Результат не совпадает с тем, что делают реальные практикующие специализации → ошибка проектирования — характер/Skills не сверены с эталоном Researcher до сборки.
4. Ветвление решений идёт по неподтверждённому тексту, а не по факту → нарушение границы детерминизм/вероятность — инструкция или модель, не Skill.
5. Работало раньше, перестало после смены модели → не баг конкретного механизма, а ожидаемая ревизия архитектуры, не разовая починка.
6. Ничего из выше не объясняет, и в мире неизвестно готового решения этого класса задач → вопрос Research, не повод изобретать самой.

## Как использовать этот Skill

1. Спроси/определи специализацию нового агента (кто это, какую задачу решает) — и запроси у Researcher эталон «как выглядит хорошо» для этой специализации (через её собственный формат компактной заметки, не читая её дом целиком самостоятельно), прежде чем проектировать характер и набор Skills.

   **Обязательный структурированный раунд вопросов, не органический диалог.** Перед тем как писать `HOME.md`/`SOUL.md`/контракт результата нового или крупно переделываемого агента — пройди через `AskUserQuestion` (или явный список вопросов, если инструмент не подходит) весь набор решений, которые определяют роль агента: границы v1, разовый или многоразовый инструмент, что именно на выходе (артефакт/структура/координация), с кем/чем взаимодействует, что явно не входит в контракт. Не полагаться на то, что 2-3 вопроса по ходу естественного разговора покроют это сами — они систематически не покрывают, находка за находкой это подтвердила. Результат раунда — часть зафиксированного дословно брифа (`workspace/<дата>-задача-*.md`), не отдельная память.

   **Глубина раунда — до реальной ясности, не до первого правдоподобного ответа.** Пять вопросов подряд с готовыми ответами — не то же самое, что реальная ясность. Раунд не закрыт, пока не пройдено явно:

   - **Конкретный референс, не абстракция.** «Покажи пример готового результата, который тебе уже нравится» и «покажи пример, который точно не подходит» — не «опиши, каким должен быть агент». Абстрактное описание роли расходится с реальным ожиданием чаще, чем кажется.
   - **Столкнуть с краевым случаем.** Не «согласны ли вы с этим планом», а конкретная гипотетическая ситуация на грани роли — где отвечающий вынужден или подтвердить границу, или её сдвинуть. Молчаливое «в целом да» на общий план не считается пройденной проверкой.
   - **Явно спросить про то, чего НЕ будет.** Не только что входит — что сознательно не входит и почему, до того как это станет неприятным открытием на приёмке.
   - **Не соглашаться с первым ответом, если он противоречит уже сказанному раньше.** Если новый ответ спорит с более ранним утверждением того же разговора — назвать противоречие прямо и попросить владельца разрешить его, не тихо взять последний ответ как более новый и более верный.
   - **Спросить, кто ещё несёт риск/цену ошибки.** Реальный клиент, юридические последствия, деньги — если такое есть в задаче, это отдельный явный вопрос, не выводится из контекста.
   - **Явно назвать инструментальные ограничения проверки, не только роли.** Прежде чем брать в работу что-то с UI/визуальным результатом — прямо сказать, какие инструменты проверки есть (HTTP/API-уровень) и каких нет (браузерная автоматизация, клик-путь), до начала сборки — не когда владелец наткнётся на это на собственном тесте.

   Раунд закрыт, когда владелец подтвердил не общий план, а конкретный список того, что будет: файлы, структура, форма результата — тот же принцип, что уже есть в `HOME.md`, «Общее «вперёд» — не то же самое, что разрешение на конкретный объём».
2. Пройди по таблице Implementation выше — для каждой строки укажи, что уже готово (Foundation), что нужно заполнить (точка расширения) и кто это делает. Для строки «Способности» — сверь кандидатов Skills с тем, что уже знает Researcher об этой специализации, и с тем, что реально есть в Skill System, прежде чем ставить через `installer`.

   **Capability Gap Analysis — явное действие, не общее «сверить».** Прочитай
   `../ПРОЕКТЫ/Skill System/registry.json` (не по памяти о том, что там уже видела раньше —
   библиотека растёт). Составь список профильных категорий специализации (для маркетолога —
   `STRATEGY`/`WRITING`, для дизайн-агента — `DESIGN`, и т.д.), пройди по ним и назови
   владельцу прямо: «в библиотеке для вашей ниши есть `X`/`Y`, не подключены — подключаем?».
   Молчаливое «скиллов достаточно» без явного перечисления кандидатов и отказа по каждому —
   не считается пройденным шагом. Применимо не только к сборке нового агента, но и к
   **аудиту или доработке уже существующего** — при любой значимой задаче на уже собранном
   агенте (`instructions/pre-task-check.md`, «Capability Gap Gate») эта же сверка повторяется,
   не только один раз на старте. Найдено 2026-09-04 (аудит Кодекса, инициирован владельцем):
   без явного требования сверка выполнялась нерегулярно, а новые скиллы в библиотеке
   (`grilling`, `humanizer`, `pricing`/`revops` и др.) не долетали до уже работающих агентов,
   для которых они профильны.
3. Не изобретай новые файлы/папки сверх списка без явной причины, зафиксированной в `DECISIONS.md`, — это нарушило бы Principle (не переизобретать структуру).
4. Перед тем как сказать «репозиторий готов» — пройди чек-лист выше построчно, не на глаз. Прохождение чек-листа означает «репозиторий собран», не «агент готов» — второе проверяется последним пунктом чек-листа, не выводится из первых девяти.

# Repository Design

## Principle

Собрать репозиторий агента — не значит изобрести структуру заново. Значит найти в уже готовом фундаменте (Foundation) точки расширения и правильно их заполнить, не трогая то, что фундамент уже решил сам. Любой репозиторий профессионального агента отвечает на один и тот же список вопросов — независимо от того, чем именно фундамент реализован сегодня:

1. Где документ, объясняющий, зачем агент существует?
2. Где устав — кто агент и как он работает?
3. Где характер/тон, специфичный для этой специализации?
4. Где профиль владельца, для которого работает агент?
5. Где память, которая верна всегда, и где — то, что меняется от сессии к сессии?
6. Где накопленные знания по темам, читаемые точечно под задачу?
7. Где переносимые способности (Skills) и как они устанавливаются?
8. Где агент оставляет результаты своей работы?
9. Где решается, что читать под конкретную задачу?
10. Как агент обновляется, не теряя личных/накопленных данных?
11. Где фиксируется история решений и их статус?
12. Где живут вопросы, на которые ещё нет ответа?

Если репозиторий не даёт ответа на один из этих вопросов явным файлом — это дыра в дизайне, а не мелочь.

## Implementation (в этом проекте — Foundation)

| Вопрос | Файл/папка Foundation | Кто заполняет |
|---|---|---|
| 1. Зачем существует | `VISION.md` | Foundation (не трогать) |
| 2. Устав | `HOME.md` | Foundation задаёт форму; специализация вписывает роль в раздел «Кто ты» |
| 3. Характер | `SOUL.md` | Специализация (точка расширения, пуст в Foundation) |
| 4. Профиль владельца | `PROFILE.md` | Заполняется по ходу знакомства с владельцем — не выдумывать заранее |
| 5. Память: устойчивая / по сессиям | `MEMORY.md` / `memory/` | Foundation задаёт механизм; агент пишет в него по ходу работы |
| 6. Знания по темам | `knowledge/` | Агент пишет по ходу работы |
| 7. Способности | `skills/` (рабочий стол) + Skill System (внешний источник) + скилл `installer` | Устанавливаются только через `installer`, не пишутся вручную в тело агента |
| 8. Результаты работы | `workspace/` | Пустой каркас на старте, агент кладёт результаты по ходу |
| 9. Что читать под задачу | `ROUTING.md` | Foundation задаёт таблицу потребностей; специализация дописывает свои строки в раздел knowledge-роутинга |
| 10. Безопасное обновление | `UPDATE.md` + `update.sh` | Foundation (не трогать) |
| 11. История решений | `DECISIONS.md` | Foundation задаёт формат (Proposal → Discussion → Locked); агент пишет записи по ходу |
| 12. Открытые вопросы | `OPEN_QUESTIONS.md` | Агент пишет по ходу |

Источник таблицы: `Foundation/03_ARCHITECTURE/FOUNDATION_ARCHITECTURE.md` и `Foundation/04_REPOSITORY/README.md` — внутренние документы этого же проекта, не внешний материал, лицензионных ограничений нет.

## Что специализация никогда не трогает

`VISION.md`, `AGENTS.md`, `UPDATE.md`, `update.sh`, механика `ROUTING.md` (можно дописывать строки под свои knowledge-файлы, нельзя менять правило «не смешивать меню и триггер-фразы») — это принадлежит Foundation. Правка этих файлов агентом без явного решения владельца — нарушение, см. `Foundation/04_REPOSITORY/DECISIONS.md`.

## Правило README и профессиональных надстроек

Найдено на трёх реальных проходах в одной сессии: (1) README Engineer открывался собственной архитектурной схемой — плохо; (2) исправление получилось коротким, но вместе со схемой выкинуло почти весь настоящий объём — тоже плохо, другая ошибка того же ремонта; (3) построчный разбор реального рыночного README (`nick-vels/skills`, 18 разделов, ни одного лишнего) показал, каким должен быть настоящий объём. Краткость и архитектурность — два разных недостатка, лечатся по-разному, нельзя чинить один и получить в подарок другой.

### Порядок содержания — приоритет, не жёсткий шаблон

1. **Одна сильная строка обещания** — что получает владелец, не как это устроено.
2. Короткое объяснение: что это, чего не нужно делать самому.
3. **Если у агента есть что показать во время или после работы** (визуальный результат, отчёт, дашборд) — показать здесь, как доказательство, раньше раздела про установку/использование, не в конце как приложение.
4. **Как этим пользоваться — через настоящий, конкретный пример** задачи/запроса, не через абстрактную категорию («у вас есть режимы поиска/файлов/трекинга» — плохо; «/задача: телеграм-бот, который принимает заявки и складывает в таблицу» — хорошо).
5. Если есть режимы/настройки работы — что переключает, что не меняется никогда ни в одном режиме.
6. **Механизмы доверия — конкретно**, не декларативно: не «мы проверяем качество», а как именно (например: отдельный агент без доступа к промежуточным документам сверяет результат с исходным текстом владельца, не с пересказом).
7. Явные границы: когда использовать, когда нет — честно называть случаи, где агент не подходит.
8. **Если агент имеет дело с чувствительным** (ключи, доступы, деньги, персональные данные) — отдельный явный раздел: что никогда не запросят, что произойдёт, если владелец всё равно передаст такое.
9. Что агент никогда не делает — короткий список жёстких границ, отдельно от «когда не подходит».
10. Практическая эксплуатация — обновление/удаление/что делать, если что-то ведёт себя не так, если это применимо к этому агенту.
11. **Техническая структура репозитория — обязательный раздел, самым последним перед мета** (не «если нужно глубже», а всегда): дерево профессионально значимых папок (`skills/`, `knowledge/`, `workspace/`, аналоги у другого агента) с короткими пояснениями напротив каждого пункта, не сплошной прозой — одна строка закрытия про формат (обычный markdown, можно открыть и прочитать конкретный файл).
12. Лицензия / мета — в самом конце.

### Визуальное качество, не только состав

Там, где содержание структурное (режимы, when/when-not, дерево файлов) — таблица или дерево с подписями читается лучше сплошного абзаца (подтверждено `nick-vels/skills`: таблицы для режимов, глубины, «когда не подходит»; дерево с инлайн-комментариями для структуры). Проза — для объяснения поведения и примеров, не для перечислений.

### Что не копировать механически

Не каждому агенту нужны все 12 пунктов — пункт появляется, потому что у **этого конкретного** агента есть соответствующее реальное поведение (дашборд — только если он правда есть; раздел про ключи — только если агент правда имеет дело с чувствительным), не по привычке или ради полноты списка.

### Различать обязательное ядро Foundation от надстройки профессии

12 строк таблицы Implementation выше — у любого агента. Надстройка, специфичная для профессии конкретного агента (глубокий процессный документ вроде `LIFECYCLE.md`, дополнительные Skills, дополнительные файлы `knowledge/`) — оправдана, только если сама профессия её требует, не потому что предыдущая сборка (например, сам Engineer) её имела. Тест перед добавлением файла сверх 12 строк: «Foundation требует / профессия требует / скопировано по привычке?» — третий ответ не считается причиной.

### Финальная проверка перед тем, как считать README готовым

Раздельно, не одним вопросом: (а) нет ли архитектурной схемы/внутреннего пайплайна как первого экрана? (б) не выхолощен ли вместе с ней настоящий объём — конкретные примеры, границы, механизмы доверия? README, прошедший только проверку (а), но не (б), не готов.

## Чек-лист «репозиторий готов»

- ☐ `VISION.md`, `AGENTS.md` на месте, не изменены относительно Foundation. `HOME.md` на месте; изменён может быть только раздел «Кто ты» (точка расширения специализации, строка 2 таблицы Implementation выше) — остальное содержимое совпадает с Foundation.
- ☐ `SOUL.md` заполнен специализацией (не пустой шаблон-заглушка).
- ☐ `PROFILE.md` либо честно пуст (агент ещё не знаком с владельцем), либо заполнен из реального интервью — не выдуман.
- ☐ Все нужные Skills установлены через `installer`, ни один не написан вручную в тело агента.
- ☐ Таблица «Мои скиллы» в `HOME.md` совпадает с реально установленным в `skills/`.
- ☐ `ROUTING.md` знает, куда вести хотя бы для главных сценариев специализации.
- ☐ `workspace/` готов принимать результаты (пуст на старте, дальше заполняется по ходу работы) — Foundation сознательно не задаёт внутреннюю структуру подпапок, это решает специализация, не додумывай за неё заранее.
- ☐ `MEMORY.md` содержит то, что верно всегда для этой специализации — не пуст без причины.
- ☐ `DECISIONS.md` и `OPEN_QUESTIONS.md` заведены (даже если пока пустые записи).
- ☐ Собранный агент проверен на настоящей задаче своей специализации, результат сверен с эталоном Researcher — не только со впечатлением сборщика.
- ☐ Результат сверен с зафиксированным дословно текстом исходной задачи (`workspace/<дата>-задача-*.md`), не с промежуточными заметками/спецификацией, написанными по ходу сборки — свежим перечитыванием файла, не по памяти диалога (`LIFECYCLE.md`, «Независимая проверка результата против исходной задачи»).
- ☐ `README.md` прошёл обе проверки из «Правило README и профессиональных надстроек»: без архитектурной схемы/пайплайна как первого экрана, и без выхолощенного вместе с ней настоящего объёма (примеры, границы, механизмы доверия) — краткость и архитектурность лечатся раздельно. Каждый файл сверх 12 строк Implementation прошёл тест «Foundation / профессия / привычка».

## Если результат слабый — куда искать причину

Не гадать. Проверять по порядку (источник — `CAPABILITY_MAP.md` Researcher, Capability 3/6/11):

1. Агент заново делает одну и ту же процедурную работу вместо готового метода → не хватает Skill.
2. Агент забывает или противоречит сам себе между сессиями → неверно выбран уровень памяти либо конфликт источников не разрешён (`instructions/memory-rules.md`, «Когда источники расходятся»).
3. Результат не совпадает с тем, что делают реальные практикующие специализации → ошибка проектирования — характер/Skills не сверены с эталоном Researcher до сборки.
4. Ветвление решений идёт по неподтверждённому тексту, а не по факту → нарушение границы детерминизм/вероятность — инструкция или модель, не Skill.
5. Работало раньше, перестало после смены модели → не баг конкретного механизма, а ожидаемая ревизия архитектуры, не разовая починка.
6. Ничего из выше не объясняет, и в мире неизвестно готового решения этого класса задач → вопрос Research, не повод изобретать самой.

## Как использовать этот Skill

1. Спроси/определи специализацию нового агента (кто это, какую задачу решает) — и запроси у Researcher эталон «как выглядит хорошо» для этой специализации (через её собственный формат компактной заметки, не читая её дом целиком самостоятельно), прежде чем проектировать характер и набор Skills.
2. Пройди по таблице Implementation выше — для каждой строки укажи, что уже готово (Foundation), что нужно заполнить (точка расширения) и кто это делает. Для строки «Способности» — сверь кандидатов Skills с тем, что уже знает Researcher об этой специализации, и с тем, что реально есть в Skill System, прежде чем ставить через `installer`.
3. Не изобретай новые файлы/папки сверх списка без явной причины, зафиксированной в `DECISIONS.md`, — это нарушило бы Principle (не переизобретать структуру).
4. Перед тем как сказать «репозиторий готов» — пройди чек-лист выше построчно, не на глаз. Прохождение чек-листа означает «репозиторий собран», не «агент готов» — второе проверяется последним пунктом чек-листа, не выводится из первых девяти.

## Integration-происхождение

Пакет частично адаптирован из карточки Integration «goose: recipe.yaml + изоляция под-рецептов» (принцип изоляции — под-агент/специализация не переопределяет родительскую структуру) и карточки «SKILL.md format» (сам формат этого файла). Полный источник и обоснование: `research/AI-Engineering/03-full-report.md` §1 (Integration), `research/AI-Engineering/02-evidence.md`.

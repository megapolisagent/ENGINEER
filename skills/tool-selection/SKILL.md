# Tool Selection

## Principle

Правило выбора инструмента формулируется по категории задачи, а не по имени конкретного сервиса — если завтра сменится провайдер поиска или харнесс, принцип не должен сломаться вместе с ним. Пять категорий, которые встречаются в работе Engineer:

1. **Нужно узнать, что уже делает рынок** (мировая практика, готовый Skill, чужой репозиторий) → инструмент поиска/исследования.
2. **Нужно прочитать/изменить файлы репозитория, который собираем** → файловые и репозиторные инструменты.
3. **Задача многошаговая, требует отслеживания прогресса** → инструмент трекинга задач.
4. **Решение реально принадлежит владельцу** (не факт, который можно найти, а выбор с несколькими допустимыми ответами) → прямой вопрос владельцу, а не догадка.
5. **Задача большая, независимая, не обязана держать основной контекст занятым** → делегирование фоновому агенту.

Если задача не попадает ни в одну категорию, или под неё нет доступного инструмента — не подменяй догадкой (`HOME.md`: «нет реального факта — пометь `[УТОЧНИТЬ]` и спроси»).

## Implementation (в этой среде — Claude Code, исправлено 2026-08-12 после реальной ошибки)

**Ошибка, реально найденная и исправленная 2026-08-12**: предыдущая версия этого раздела утверждала «не предполагай доступность Exa/Firecrawl/Context7» и подавала это как единственный критерий — не рассматривать их. `claude mcp list` показал, что все три реально подключены и вызывались в этой же сессии. Причина ошибки — смешение двух разных вопросов в одно суждение. Дальше они разделены явно, по находке Researcher (`OPEN_QUESTIONS.md`, «Как зрелые системы различают…»):

| Слой | Вопрос | Как проверить у себя |
|---|---|---|
| **Доступно** | Физически подключено прямо сейчас? | `claude mcp list` — не предполагать, проверить |
| **Принадлежит** | Закреплено за этим проектом (переедет с `git clone`)? | Есть запись в `.mcp.json` проекта? У ENGINEER такого файла нет — значит нет, даже если «доступно» |
| **Разрешено** | Технически позволено вызывать? | `.claude/settings.json`/`settings.local.json`, `allow/ask/deny` |
| **Подходит для задачи** | Стоит ли использовать именно здесь? | Решение по категории задачи (раздел Principle выше), не по факту подключения |

Практический вывод: `mcp__exa__*`, `mcp__firecrawl__*`, `mcp__hackernews__*`, `mcp__youtube-transcript__*`, `context7` — не принадлежат ENGINEER как проекту (нет `.mcp.json`), но это не значит «не рассматривать». Перед задачей категории 1 (мировой поиск/исследование) — проверить `claude mcp list`, не предполагать заранее ни доступность, ни недоступность.

**Вторая находка того же дня**: Researcher, имея Exa реально доступной, ни разу её не вызвала — не из-за правила (у неё такого запрета не было), а потому что искала инструмент через `ToolSearch` с запросом, называющим уже известные имена («WebSearch WebFetch»), а не открытым вопросом. Открытый запрос (например, «инструмент для веб-поиска») с большей вероятностью вытащит альтернативу, которая не пришла в голову по привычке. Перед задачей категории 1, если результат первого инструмента слабый — стоит хотя бы раз попробовать открытый `ToolSearch`, не только называть уже знакомое.

При свежем развёртывании Engineer (`git clone` по `README.md` Foundation) сессионные MCP (не задекларированные в `.mcp.json`) не появятся сами — это не изменилось, только уточнено, что «не появится само» ≠ «не нужно рассматривать, если появилось».

**Явно не проверено в моменте**: специализированный GitHub-MCP, Playwright/Browser — проверь через `ToolSearch`/`claude mcp list` перед использованием, не по памяти этой записи. Если недоступны — `WebFetch`/`Bash`+`gh` как fallback для GitHub-специфичных задач.

## Fallback

Если ни один инструмент не подходит под задачу — сначала `ToolSearch` (могут быть отложенные инструменты, ещё не загруженные в контекст) с ключевыми словами задачи. Если и это не даёт результата — честно сказать, что подходящего инструмента нет, а не имитировать результат другим инструментом.

## Integration-происхождение

Владелец назвал недостающим (2026-08-11): не список конкретных MCP, а именно правила выбора — «когда Exa, когда Context7, когда Filesystem» и т.д. Реализовано как принцип по категории задачи + implementation-таблица, актуальная на дату создания, а не подгонка под примеры, названные при обсуждении, которые в этой среде не подтвердились. Источник обсуждения: `research/AI-Engineering/03-full-report.md` §1 не содержит отдельной карточки под tool selection — это прямое требование владельца, не рыночная находка, обозначено как таковое честно.

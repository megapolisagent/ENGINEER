# Skill Auditor
## Аудит и нормализация скиллов под стандарт `skill-authoring`

> Не создаёт новые скиллы — приводит существующие или донорские (принесённые извне) в соответствие с каноном `skill-authoring`. Работает по одному скиллу за раз внутри партии, каждый шаг фиксируется в `AUDIT_LOG.md`.

## Фаза 1 — Context-Investigator (экономная разведка)

Цель: понять, что лежит в папке, не раздувая контекст чтением всего подряд.

- Запрещено вычитывать все файлы папки в память подряд.
- Структуру сканировать только командами терминала: `Get-ChildItem -Name` / `tree` (PowerShell) или `find` (Bash) — не построчным `Read` каждого файла.
- Назначение каждого скилла определять по первым 25 строкам его `SKILL.md` — это YAML frontmatter (`name`, `description`) плюс открывающие строки тела. Полное тело читается только на Фазе 3, и только для скиллов, прошедших Triage со статусом «Взять».

## Фаза 2 — Triage (классификация доноров)

Для партии скиллов составляется таблица первичного отбора:

| Название | Категория | Статус | Обоснование |
|---|---|---|---|
| `<skill-name>` | discipline / technique / pattern / reference | Взять / Пропустить | одна строка — почему |

- **Категория** — по таблице типов из `skill-authoring` (дисциплина, техника, паттерн, справочник).
- **Статус «Пропустить»** ставится для: дублей уже существующего в системе скилла, узкоспецифичных под чужой стек/проект решений, скиллов без применимости ни к одному агенту экосистемы.
- На этой фазе же отсекаются платформенные артефакты и привязки к автору-донору: манифесты чужих рантаймов (`agents/*.yaml`), инсталляторы конкретных пакетов, персональные ссылки — само их наличие не повод пропускать скилл целиком, это находка для Фазы 3, а не приговор.

## Фаза 3 — Нормализация (Clean-up)

Применяется только к скиллам со статусом «Взять». Для каждого:

1. **Frontmatter.** Убрать из `description` описательный пересказ («что делает»): оставить только фразы-триггеры вызова — конкретные слова, ситуации, симптомы, по которым агент или человек реально позовёт скилл. Строка, которая пересказывает механику работы скилла, в `description` не остаётся, даже если она информативна — такому место в теле.
2. **Объём.** Если ядро `SKILL.md` превышает 500 строк — обязательный вынос: справочники, таблицы, методички → `references/`; эталонные примеры и решения → `examples/`; исполняемый код → `scripts/`. Разбивка ниже 500 строк не обязательна сама по себе — критерий не «можно вынести», а «превышен лимит или ядро реально перегружено деталями, которые не нужны каждому прогону».
3. **Автономность.** Удалить чужие манифесты (`agents/openai.yaml` и аналоги), специфические скрипты инсталляции под внешние пакетные менеджеры, хардкод путей/команд к донорским пакетам (`/setup-*`, сторонние `docs/...`). Если удаляемая строка несла полезную логику (не только чужую привязку) — заменить на локальный эквивалент, а не молча вырезать функциональность; если эквивалента нет — явно отметить пробел в `AUDIT_LOG.md`, а не маскировать его.
4. Каждая правка — точечная замена по правилам `.claude/rules/safe-editing.md`, не переписывание файла с нуля.

## Фаза 4 — Журналирование

Каждый обработанный скилл — одна запись в `AUDIT_LOG.md` (в корне партии/аудита), формат:

```text
## <skill-name>
- Статус: Взят / Пропущен
- Диффы: <краткий список правок — frontmatter / структура / автономность>
- Вердикт: <прошёл нормализацию без замечаний | прошёл с оговоркой (какой) | пропущен (почему>
```

Запись создаётся сразу после Фазы 3 для этого скилла, не пачкой в конце — так партия остаётся восстановимой, если аудит прервётся на середине.

## Когда НЕ применять

- Для написания нового скилла с нуля — это `skill-authoring` (RED/GREEN/REFACTOR), а не нормализация существующего.
- Для правки одного своего скилла по ходу обычной работы без цели «привести к стандарту» — обычный `Edit` без протокола фаз.

## Checklist

- [ ] Структура партии просканирована командой терминала, не построчным чтением
- [ ] Triage-таблица составлена до начала правок
- [ ] `description` каждого взятого скилла — только триггеры
- [ ] Объём ядра проверен, превышения разнесены по `references/`/`examples/`/`scripts/`
- [ ] Чужие манифесты и донорские привязки удалены или заменены локальным эквивалентом
- [ ] `AUDIT_LOG.md` содержит запись по каждому обработанному скиллу

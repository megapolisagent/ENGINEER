# Pre-task check

Перед значимой задачей — ответить на:

1. Что я должен получить?
2. Что обязательно должно быть покрыто?
3. Что не входит в задачу?
4. Как будет проверено, что задача выполнена?
5. Что мне понадобится для выполнения? Если среди этого — исполняемый файл из внешнего источника (клонированный скилл-репозиторий, скачанный установщик) — см. `instructions/external-script-safety.md` прежде чем запускать.
6. Что я обязан сохранить/зафиксировать по ходу?
7. Когда я должен остановиться?
8. Предусматривает ли задача изменение моих правил, инструментов или архитектуры? Если нет — не менять их по ходу работы без отдельного разрешения.

## Локальная адаптация

Для задач-ресерчей (Researcher, доменный/рыночный/open-source поиск) ответы на пункты 1, 2, 5, 7 обязаны быть **видны в самом отчёте**, написаны ДО начала инструментов — не восстановлены задним числом под то, что получилось. Отчёт без видимого плана перед разделом находок — не считается завершённым для этого класса задач.

**Delegation Gate — прежде чем поручить задачу другому агенту.** Диспетчеризация в чужой репозиторий (headless `claude -p`, `Agent`, `SendMessage`) — сначала прочитать `instructions/pre-task-check.md` и правила делегирования/показа плана владельцу в инструкциях и `DECISIONS.md` целевого агента, не полагаться на память о том, что там написано. Реальный сбой, из-за которого правило внесено (2026-09-04): headless-запуск Researcher по брифу об источниках данных Avito сделан без проверки её же `instructions/pre-task-check.md`, где явно записано «для существенного исследования — показать краткий pre-task check владельцу и дождаться подтверждения, прежде чем начинать поиск» — пункт пропущен, хотя сам файл был доступен для чтения за секунду. Тот же класс ошибки, что весь этот файл требует ловить у Codex/других инструментов — применить его и к себе, диспетчеру.

**Size Gate — проверка при завершении задачи, затронувшей `DECISIONS.md` любого репозитория.** Сессия не считается закрытой, если активный `DECISIONS.md` целевого репозитория превышает 50 КБ или содержит более 10 закрытых (Locked/Отклонено) записей — сначала запустить `scripts/archive_decisions.py <путь к DECISIONS.md>`, перенос закрытых записей в `DECISIONS_ARCHIVE.md` механический, ничего не удаляется. Внесено 2026-09-03 по итогам архивации `DECISIONS.md` трёх агентов (ENGINEER, Marketing Strategist, Legal Constructor — все трижды превышали порог до этого дня), см. `advisory_enhancement_plan.md`, Блок 1.1.

**Deprecation Parity Gate — прежде чем пометить существующий артефакт (Skill, инструмент, файл) DEPRECATED/OBSOLETE/«заменён X».** Обязательно, до пометки:
1. Прочитать оба артефакта (старый и новый) построчно, не по названию/описанию.
2. Составить список реальных возможностей старого (функции, скрипты, автоматизация, data flow).
3. Для каждой возможности проверить: перенесена ли она в новый, пусть в другой форме?
4. Что не перенесено — зафиксировать явно, с причиной (не нужно / нет инфраструктуры / отложено).
5. Только после этой сверки — ставить DEPRECATED, с перечислением непереехавшего в самой записи `evidence.json`/`DECISIONS.md`.

Пометка «заменён» без построчной сверки — не ускорение, а технический долг: другой агент решит, что возможность всё ещё доступна, хотя её нет. Внесено 2026-09-04 по итогам независимого разбора Codex: `skill-creator` (327 строк, 8 Python-скриптов, eval-инфраструктура) помечен DEPRECATED 2026-08-13 с причиной «заменён `skill-authoring`» (77 строк, ноль скриптов) — на следующий день после того, как сам capability-аудит (2026-08-12, `DECISIONS_ARCHIVE.md`) предупредил: перенос требует адаптации eval-инфраструктуры, иначе «риск бегло сделанного авторства, не решение». Предупреждение проигнорировано, сверки не было. Решение реверсировано тем же днём — см. `Skill System/DECISIONS.md`.

**Capability Gap Gate — при значимой задаче на уже собранном агенте (аудит, доработка, разбор жалобы владельца), не только при первой сборке.** Перед тем как считать задачу завершённой — явно зафиксировано в отчёте: сверен ли профиль этого агента с `../ПРОЕКТЫ/Skill System/registry.json` (`skills/repository-design/SKILL.md`, «Capability Gap Analysis»), и если да — какие профильные скиллы библиотеки уже подключены, каких не хватает, что явно предложено владельцу. Если сверка не проводилась в рамках этой задачи — назвать причину (профиль агента не менялся с последней сверки / задача узкотехническая, не затрагивает набор способностей), не молчать. Внесено 2026-09-04 (владелец, по итогам разбора стороннего анализа её архитектурного бота): без явного гейта библиотека Skill System росла (`grilling`, `humanizer`, `grill-me`/`grill-with-docs` и т.д.), а уже собранные агенты, для которых эти скиллы профильны, не получали предложения их подключить.

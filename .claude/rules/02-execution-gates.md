# Execution Gates

## Pre-task checklist (значимая задача)
1. Что должен получить владелец?
2. Что обязательно покрыто?
3. Что не входит в задачу?
4. Как проверяется выполнение?
5. Что понадобится для выполнения? Внешний исполняемый файл в списке → см. `external-script-safety.md` до первого запуска.
6. Что сохранить/зафиксировать по ходу?
7. Когда остановиться?
8. Задача меняет правила/инструменты/архитектуру? Нет → не менять по ходу без отдельного разрешения.

## Research-задачи
Пункты 1, 2, 5, 7 — видны в самом отчёте, написаны до начала работы инструментами, не восстановлены задним числом под результат.

## Delegation Gate
Перед передачей задачи другому агенту (headless `claude -p`, `Agent`, `SendMessage`): прочитать pre-task/delegation-правила целевого агента заново, не полагаться на память о них.

## Deprecation Parity Gate
Перед пометкой артефакта DEPRECATED/OBSOLETE/«заменён X»:
1. Прочитать старый и новый артефакт построчно.
2. Составить список реальных возможностей старого.
3. Для каждой — проверить, перенесена ли в новый.
4. Непереехавшее зафиксировать явно, с причиной.
5. Развилка:
   - Есть непереехавшее → DEPRECATED (обратимо), пробел — в `evidence.json`.
   - Строгий суперсет, потерь нет → старое удаляется целиком, не архивируется.

## Capability Gap Gate
При значимой доработке уже собранного агента: сверить его профиль с `registry.json` Skill System (`skills/repository-design/SKILL.md`, Capability Gap Analysis). В отчёте явно указать: сверено или нет, что уже подключено, чего не хватает.

## Composability & Tooling Gate
Перед сдачей нового или отредактированного `SKILL.md`:
1. Одна ли это функция? Несколько «Модуль N» с разным входом/выходом/владельцем решения → разбить на отдельные фокус-скиллы.
2. Для каждого шага с числовым/детерминированным результатом — есть реальный скрипт в `tools/` или `scripts/`, не расчёт прозой?
3. Гейт применяется и к уже существующим скиллам, не только к новым.

Механическая проверка: `.claude/tools/check_skill_composability.py <путь к .claude/skills агента>` — выдаёт факты, не вердикт.

## Canon Sync Gate
При значимой доработке агента — сверить его существующие `SKILL.md`/`CLAUDE.md` с текущей версией канона (`docs/architecture/pipeline-architecture.md` и другие правила), даже если сама задача узкотехническая. Найденный дрейф называть в отчёте, не откладывать молча.

## Proportional Review Gate
Решение меняет методологию/архитектуру агента → глубина проверки пропорциональна масштабу и риску:
- Небольшое, чётко ограниченное изменение → проверка владельцем + прогон на реальной задаче.
- Фундаментальная архитектура, роли, или изменение затрагивает много агентов → независимая проверка отдельным изолированным ходом рассуждений (`reviewer`, model haiku, см. `.claude/agents/reviewer.md`).

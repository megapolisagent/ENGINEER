# Capability Resolver

> Источник: архитектурный паттерн из `MAIN_ASSISTANT/PLATFORM_PLAYBOOK.md` (другой, не-Foundation агент той же экосистемы), перенесён с разрешения владельца 2026-08-19. Реально применён и проверен на настоящей задаче в ENGINEER — заполненный Platform Decision Record привёл к решению строить агента-маркетолога через Adopt существующей архитектуры, а не с нуля, — не гипотеза и не только диалог.

## Потребность отдельно от инструмента

Прежде чем решать, какой конкретный Skill/агент/инструмент использовать — сначала назвать класс потребности, не инструмент. Смешивание этих двух решений в одно повышает риск выбрать привычное, а не то, что реально нужно задаче.

Резолвинг «класс потребности → конкретный инструмент» — механический шаг, специфичный для набора возможностей конкретного агента (какие Skills/MCP/агенты у него реально есть) — описывается в специализации, не здесь. Здесь — только сама дисциплина двух разделённых шагов.

## Закон: внешняя разведка обязательна всегда — не «если дома нет»

**Ошибка, которую этот закон закрывает:** «дома уже что-то лежит → значит рынок можно не смотреть». Наличие скилла в Skill System ничего не говорит о его актуальности — библиотека может держать три устаревших инструмента, пока рынок за это же время выпустил десять более мощных и чистых. Изнутри библиотеки этот разрыв не виден никогда — его видно только снаружи. Решение владельца, 2026-09-09.

Поэтому при сборке или модернизации **любого** агента внешняя разведка обязательна **всегда**, независимо от того, есть ли уже дома подходящий на вид скилл. «У нас уже есть Х» — не основание пропустить разведку, а первая половина Challenger vs Champion: без свежего Champion снаружи не с чем сравнивать.

**Минимум три независимых источника, каждый раз:**

1. **`find-skills`** — дом-ограниченная версия, единственная разрешённая команда: `DISABLE_TELEMETRY=1 npx skills@1.5.23 find <запрос> [--owner <owner>]` (см. `Skill System/skills/find-skills/SKILL.md` — `add`/`init`/`update`/`experimental_sync`/`use` через этот инструмент под категорическим запретом).
2. **Официальные репозитории вендора** — прежде всего `anthropics/skills`, плюс официальный каталог/документация профильного вендора под роль агента, если он есть.
3. **Открытый GitHub/сообщество** — `WebSearch`/`WebFetch` за пределами одного агрегатора: awesome-list, обзоры, репозитории конкретных практиков в нише роли — не только то, что проиндексировал `skills.sh`.

Источник, который реально недоступен (нет сети, недоступен эндпоинт) — называть прямо в отчёте с `[УТОЧНИТЬ]`, не пропускать молча и не заменять двумя источниками вместо трёх.

**Сверка — Challenger vs Champion** (протокол `skill-auditor`): для каждого внутреннего скилла под эту роль — задать вопрос в лоб: то, что нашлось снаружи, сильнее, свежее, чище нашего Champion, или наш всё ещё держит планку? Разбор ссылки в диалог не считается: как и в `01-data-discipline.md`, `SKILL.md` кандидата читается целиком лично, не по описанию из поиска.

**Вывод — всегда один из трёх, вслух:** оставить внутреннее как есть / обновить внутреннее / добавить новое внешнее. Установка нового или обновлённого — только через канонический конвейер (`CLAUDE.md` §7): физическая копия, symlink запрещён категорически, никаких `npx skills add`.

## Platform Decision Record — обязательный артефакт при сборке или модернизации агента

Не только перед тем, как завести новый Skill, subagent или репозиторий агента — при **любой** сборке или модернизации, даже если исход, скорее всего, «оставляем как есть». Короткий рабочий артефакт прямо в ответе (не отдельный файл, не отчёт постфактум):

```
Platform Decision Record

Задача: [одна строка]

Внешняя разведка (обязательна всегда, минимум 3 независимых источника):
1. find-skills (DISABLE_TELEMETRY=1 npx skills@1.5.23 find <запрос>) — [что нашли / ничего]
2. Официальные репозитории (anthropics/skills, вендор роли) — [что нашли / ничего]
3. Открытый GitHub/сообщество (WebSearch/WebFetch) — [что нашли / ничего]

Challenger vs Champion: [снаружи против внутреннего — устарело ли наше, есть ли явно сильнее, чего не хватает]

Рассмотрено:
✓/✗ [существующая практика/агент/Skill/инструмент, внутренний и внешний] — рассмотрен, нужен / не нужен, почему

Используем: [что уже есть, закрывает задачу]
Не используем: [что рассмотрено и отклонено — одна строка почему]

Недостающая возможность: [что реально не умеет уже существующее] / «отсутствует»

Вывод: оставить внутреннее / обновить внутреннее / добавить новое внешнее
[если добавляем или обновляем — одна строка что именно; установка строго физической копией, symlink запрещён]
```

Не заменяет `02-execution-gates.md` — это его видимый результат применительно к решению «строить или взять готовое», не отдельный процесс.

## Механизм монтирования скилла под задачу

1. Определить роль/домен задачи → найти нужный скилл в `LIBRARY.md`/`index.html` по категории (`CORE`/`RESEARCH`/`STRATEGY`/`WRITING`/`ENGINEERING`/`DESIGN`) или прямым поиском по имени.
2. Прочитать `Skill System/skills/<имя>/SKILL.md` целиком (не по строке дашборда — дашборд только для маршрутизации, не источник истины) и учесть его статус (`DRAFT`/`EVALUATED`/`VERIFIED`/`NEEDS REVIEW`/`DEPRECATED` — см. `CONTRIBUTING.md` библиотеки).
3. Скопировать (не переместить) папку скилла из `Skill System/skills/<имя>/` в `.claude/skills/<имя>/` целевого агента — целиком, включая `references/`/`examples/`/`scripts/`. Только физическая копия файлов — symlink запрещён категорически, для 100% автономности каждого агента (решение владельца, 2026-09-09).
4. После значимого использования — `python scripts/skillctl.py record-usage <имя>` в самой Skill System (не в агенте, куда скилл смонтирован), чтобы статус в реестре отражал реальную, не декларативную проверенность.
5. Если для роли уже есть покрывающий её скилл — сначала протокол Challenger vs Champion (Merge/Replace/Reject, см. `skill-auditor`), не монтировать вслепую поверх существующего.

**Новый домен — новый кластер.** Если задача не покрывается ни одной из существующих строк каталога и не подходит по смыслу ни в один текущий кластер — не подгонять силой; открыть новый кластер в `CATALOG.md` (см. правило масштабирования в его шапке).

**Исключение: базовый инструментарий движка.** `skill-authoring` и `skill-auditor` — не каталожные объекты Skill System, а внутренняя инфраструктура самого Engineer (запуск цикла создания/аудита скиллов). Живут в `.claude/skills/` напрямую, не проходят регистрацию в `registry.json`/intake-конвейер и не участвуют в Challenger vs Champion сами на себя — решение владельца, 2026-09-09. Остальные рабочие утилиты, смонтированные не из Skill System (например, через `npx skills` из внешнего источника), фиксируются в `skills-lock.json` — это и есть их источник истины о наличии, не `registry.json`.

## Веб-доступ по умолчанию — Exa, не встроенные WebSearch/WebFetch

Резолвинг «нужен веб-доступ → какой конкретный инструмент» для этого дома: по умолчанию **Exa** (`mcp__exa__web_search_exa`/`mcp__exa__web_fetch_exa`), не встроенные `WebSearch`/`WebFetch`. Переход на встроенные — только если Exa вернула пусто/ошибку на конкретном запросе, или скилл прямо предписывает другое (пример: `telegram-research` — `curl` через `Bash`, не Exa/WebFetch, для чтения самих постов).

Перенесено из `AI Marketing Strategist/.claude/rules/tool-preference.md` (проверено напрямую 2026-09-14 — на JS-рендеренном сайте застройщика `WebFetch` давал пустоту, Exa отдала полную страницу). Пропуск этого правила у себя обнаружен владельцем 2026-09-19 — использован `WebSearch` вместо Exa при внешней разведке, хотя разрыв был найден раньше в этом же разговоре и не закрыт до конца.

## Та же дисциплина — перед тем как заявить «источник недоступен»

Резолвинг применяется не только к «строить новое», но и к обратному выводу — «этой возможности нет». Проверка MCP-серверов и разрешённых доменов у своего агента — не полная проверка. Прежде чем написать «X недоступен» — проверить: (1) есть ли у соседнего агента дома уже готовый Skill или метод, решающий ту же задачу другим путём (`Skill System/CATALOG.md`, `skills/` соседних агентов); (2) обходит ли уже разрешённый инструмент (например, `Bash`, если разрешён без ограничений) ту систему разрешений, в которой ищется недостающий доступ.

**Реальный случай (2026-08-28, ENGINEER):** заявлено «Telegram недоступен Researcher» на основании проверки только `.mcp.json` и разрешённых доменов WebFetch. Рабочий метод существовал — `telegram-research` (публичные каналы читаются `curl` через `Bash`, не через WebFetch/MCP) — уже провалидирован и один раз реально сработал (`AI Marketing Strategist`, медиааудит конкурентов, 2026-08-20). `Bash` у проверяемого агента был разрешён без ограничений — обходной путь был доступен весь заход.

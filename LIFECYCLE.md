# Lifecycle Engineer — рабочая инструкция, не карта для человека

> Это подробный технический документ. Простую картину смотри в `README.md`. Здесь — по каждому механизму: FACT (реально работает), PROPOSED (спроектировано, не построено), GAP (пока нет вообще). Не выдаёт желаемое за существующее.

---

## 1. Роль Engineer — за какой результат отвечает

**FACT.** `DECISIONS.md`, Locked 2026-08-12: «Engineer отвечает за то, чтобы агент как техническая система устойчиво достигал требуемого профессионального результата. Foundation, Skills, инструкции, tools, permissions, memory, interfaces, validation и другие технические механизмы являются средствами этой ответственности, а не её границами.»

Граница Craft vs Engineering (тот же Locked): Engineer не определяет профессиональную методологию предметной области вместо специалиста/Researcher — отвечает за то, чтобы техническая система позволяла результат достигать, проверять и воспроизводить.

---

## 2. Как принимает решение

**FACT** — `HOME.md`, «Вход в задачу»: три оси — Impact, Uncertainty, Complexity. Все низкие → действует сам, без вопросов. Хотя бы одна высокая → не гадает, задаёт 2–3 вопроса, ждёт подтверждения. Если решение может изменить правила собственной работы — сначала проверяет `DECISIONS.md`, не решён ли вопрос уже.

**Когда исследует** — если ответа не хватает в собственных файлах и вопрос требует знания о мире/профессии — не изобретает, передаёт вопрос Researcher (см. §7).

**Когда эскалирует владельцу** — GAP на чёткий критерий «эскалировать/не эскалировать» отдельно от Entry Gate; сейчас это тот же общий триаж, специального правила для «когда точно нужен владелец» нет.

**FACT — правило перехода в Locked**: только по явному слову владельца («принимаем», «зафиксируй», «LOCKED») — никогда из тона. Решения с высоким радиусом поражения (меняющие методологию, не разовую задачу) требуют независимой проверки отдельным ходом рассуждений перед `Locked` — если владелец явно принимает риск без неё, это фиксируется в самой записи, а не скрывается (см. `DECISIONS.md`, записи 2026-08-11 и 2026-08-12 про роль Engineer).

## 3. Как строит нового агента — текущий lifecycle

| Этап | Статус |
|---|---|
| Потребность + специализация | **GAP** — нет отдельного критерия «нужен ли агент», только общий Entry Gate |
| Эталон профессии от Researcher | **FACT** — практиковалось дважды, критерий ответа фиксируется до запроса (`OPEN_QUESTIONS.md`) |
| Foundation как основание | **FACT (для Engineer)** — впервые реально проверено 2026-08-12 (`diff` с текущим Foundation), 0 расхождений сверх точек расширения. **GAP** — процедура не проверена на агенте, отличном от Engineer |
| Skills: статус и подключение | **FACT** — полный цикл замкнут: есть → зарегистрирован → Evaluation (`skillctl.py`) → установлен через `installer` (реально прогнан end-to-end, обе ветки) → использование зафиксировано (`knowledge/skill-usage-observations.md`) |
| tools/MCP/permissions | **FACT (для Engineer)** — таблица `tool-selection` отражает реальную границу «принадлежит Engineer» vs «сессионное»; `.mcp.json` осознанно не создан (нет реальной зависимости) |
| Контракт результата | **FACT (для Engineer)** — раздел «Контракт результата» в `HOME.md`. **GAP** — не обобщён как обязательный шаг в `repository-design` для будущих агентов |
| Сборка репозитория | Частично — 12-строчная таблица компонентов есть (`repository-design`), порядок сборки между ними не определён |
| Техническая готовность | **FACT** — чек-лист «репозиторий готов» реально прогнан дважды, находит настоящие проблемы |
| Профессиональная проверка | См. §9–10 — заменена более простой моделью, эталон не изобретается заранее |

## 4. Как работает с Foundation / Домом

**FACT.** `update.sh` до 2026-08-12 перезаписывал `HOME.md`/`AGENTS.md`/`ROUTING.md`/`skills/` целиком, стирая специализацию (роль, таблицу Skills, добавленные строки роутинга, донастройку `installer`) — эмпирически подтверждено прогоном на копии (`workspace/2026-08-12-update-sh-fix-evidence.md`). Исправлено локально: `update.sh` теперь трогает только `instructions/`, включая отказ от самообновления — иначе апстрим Foundation вернул бы старый список при первом же запуске.

**GAP.** Правка не попала в реальный источник Foundation (`https://github.com/megapolisagent/FOUNDATION.git`) — показана владельцу как патч, не применена. До тех пор `update.sh` не обновляет сам себя — осознанное ограничение, не забывчивость.

**FACT.** Самоизменение устава (`HOME.md`/`SOUL.md`/`ROUTING.md`) требует прочитать `DECISIONS.md`, ответить на 5 вопросов (`UPDATE.md`) и предложить как `Proposal`, не тихо.

## 5. Как ищет и выбирает Skills / plugins / MCP / tools

**FACT — Skills.** Полный lifecycle (собран и закрыт 2026-08-12):

```
Skill есть (origin: own/adapted) → зарегистрирован (registry.json, category, DRAFT по умолчанию)
   → Evaluation (skillctl.py evaluate, tested/observed, human approval на переходе к VERIFIED)
   → установлен (installer: install / update / расхождение — 3 ветки, все реально прогнаны)
   → реально используется (evidence в knowledge/skill-usage-observations.md)
   → результат использования проверен (замыкается на Evaluation)
```

**FACT — plugins.** Нет слоя plugins у Engineer вообще — проверено прямо (нет файлов, нет `.claude/settings.json`). Не строится ради полноты таблицы — нет реальной задачи, которая бы его требовала.

**FACT — MCP/tools.** Engineer использует только native-инструменты харнесса (`Read/Write/Edit/Bash/PowerShell/WebFetch/WebSearch/Task-tools/Artifact`). Рыночно-исследовательские MCP (`mcp__exa__*`, `mcp__firecrawl__*`, `mcp__hackernews__*`, `mcp__youtube-transcript__*`) — видны в сессии, но принадлежат профилю Researcher, не задекларированы и не нужны Engineer по роли.

## 6. Как проверяет и устанавливает найденные capabilities

**FACT.** Только через `installer` — три ветки: установка (папки нет), обновление (совпадает по факту наличия, перезаписать), расхождение (содержательно разошлось — не решает сама, фиксирует в `DECISIONS.md`, не перезаписывает молча ни в одну сторону). Все три ветки реально исполнены на настоящих Skills Engineer, не только описаны.

**GAP.** Установка/обновление НЕ отдельного Skill, а целой внешней системы/репозитория (например, если Researcher находит готовую чужую реализацию) — не покрыто ничем. Единственный существующий аналог (`SKILL-SYSTEM.md` §6, origin/adapted) работает на уровне одного файла-способности, не целого репозитория.

## 7. Как взаимодействует с Researcher

**FACT.** Нет канала агент↔агент (`COMMUNICATION.md`: «не покрыто ничем в текущей версии»). Весь реальный обмен этой сессии (вопрос про Exit Gate, сверка `repository-design` с практикой) шёл через владельца как реле — вручную, не автоматически.

**FACT.** У запроса к Researcher есть рабочая форма: узкий вопрос + критерий ответа, зафиксированный **до** поиска (`OPEN_QUESTIONS.md`). У Researcher — собственный письменный контракт выхода (`MISSION.md`), но формат именно точечного (не полного Report) ответа не формализован нигде, сложился по факту использования.

**GAP.** Автоматическая передача находок Researcher (например, из отчёта агента) — не спроектирована и не построена.

## 8. Как передаёт результат владельцу / другим компонентам

**FACT.** `HOME.md`, «Контракт результата» — по типу входа определён обязательный выход (репозиторий+чек-лист+evidence / отчёт FACT-GAP-INFERENCE / правка+запись в `DECISIONS.md` или дневник). Правило «никогда не выдумывать факт, помечать `[УТОЧНИТЬ]`» — действует всегда.

---

## 9. Как созданный агент сообщает о своей работе Engineer

**PROPOSED, ничего не построено.** Формат (по спецификации владельца, 2026-08-12): задача → результат → Skills использованы → tools/MCP/plugins использованы → ошибки → что сделано иначе → что не получилось → что сам агент считает нужным улучшить.

Открытые технические вопросы, не решённые до начала строительства:
- Может ли агент в отдельном проекте физически писать файл в папку Engineer — правдоподобно (файловая система не изолирована жёстко по проектам), но не проверено для чужого агента и не прописано ему как обязанность при сборке.
- «Engineer автоматически смотрит, без владельца» — требует планового пробуждения (в среде есть такая возможность), но сама связка «отчёт лежит → Engineer разбудили → посмотрел → решил» не собрана и не испытана ни разу.

## 10. Как Engineer обнаруживает проблему и что делает дальше

**FACT — для Skills.** Находка → `skillctl.py evaluate` → статус в Skill System, человеческое одобрение на переходе к `VERIFIED` — реально работающий, только что закрытый цикл.

**FACT — общий диагностический ход** (`repository-design`, «Если результат слабый»): проверять по порядку — не хватает Skill → уровень памяти/конфликт источников → характер/Skills не сверены с эталоном → нарушение границы детерминизм/вероятность → ожидаемая ревизия архитектуры → вопрос Research. Называет категорию причины.

**GAP.** Для проблемы, найденной НЕ в собственной работе Engineer, а в реальной работе созданного им агента (Фаза 9 выше) — маршрута «куда конкретно записать находку и что сделать дальше» не существует, только диагностическая категория.

## 11. Что Engineer имеет право менять сам, а где нужно решение владельца

**FACT — можно самому:**
- собственная память (`MEMORY.md`, `memory/`, `knowledge/`) — «записывать без спроса» (`HOME.md`);
- Skills, которые не входят в список Foundation (`installer/SKILL.md` — не в списке «специализация никогда не трогает»);
- рядовые находки/правки, не проходящие входной фильтр значимости.

**FACT — только через `Proposal` → явное слово владельца → `Locked`:**
- `HOME.md`/`SOUL.md`/`ROUTING.md` (устав) — обязательны 5 вопросов из `UPDATE.md` перед предложением правки;
- всё, что меняет методологию работы, а не разовую задачу — требует независимой проверки перед `Locked`, если владелец явно не принял риск без неё.

**FACT — никогда не сам, независимо от слова владельца в моменте:**
- `VISION.md`, `AGENTS.md`, `UPDATE.md`, `update.sh`, механика `ROUTING.md` — принадлежит Foundation (`repository-design/SKILL.md`, «Что специализация никогда не трогает»);
- сам источник Foundation (`https://github.com/megapolisagent/FOUNDATION.git`) и Skill System как общий ресурс — правки только показываются, не применяются самостоятельно.

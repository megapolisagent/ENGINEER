# Протокол сквозного аудита агента через Codex (Full Repository Deep Dive)

> Применяется Инженером после сборки или реорганизации агента.
> Codex изучает проект целиком, без исключений, оценивая как смысловую архитектуру, так и техническую чистоту.

---

## 1. Команда запуска

Проверено на реально установленном `codex-cli 0.147.0` (`codex exec --help`) — флага `--file` у `codex exec` не существует, промпт передаётся позиционным аргументом или через stdin. Рабочая папка агента задаётся флагом `-C`, поэтому в самом брифе плейсхолдер пути не нужен.

Инженер запускает аудит из своей рабочей директории (ENGINEER), указывая путь к папке проверяемого агента через `-C`:

```bash
codex exec -C "<путь к папке агента>" - < instructions/codex_deep_audit_prompt.md
```

Бриф — `instructions/codex_deep_audit_prompt.md` (см. рядом).

## 2. Известный риск: реальные секреты в проверяемом репозитории

Задача брифа — читать проект «без исключений», включая `.env` и кэши токенов. Если в папке агента лежат настоящие ключи/токены (частый случай для уже подключённых интеграций), их содержимое уходит в контекст Codex, а значит — на серверы провайдера модели (если не используется `--oss`/локальный провайдер). Бриф просит Codex НЕ цитировать сам секрет в отчёте, только факт и путь — это снижает риск утечки через отчёт, но не отменяет сам факт передачи содержимого файла модели при выполнении запроса.

**Перед первым запуском на репозитории с реальными ключами** — явно решить с владельцем, допустимо ли это для конкретного провайдера, или сначала исключить файлы с секретами из просмотра (например, временно переименовать/переместить `.env` и файлы кэша токенов за пределы проверяемой папки на время аудита).

## 3. Сквозная матрица тотального аудита

Codex структурирует отчёт по трём обязательным блокам.

### Блок 1. Смысловая архитектура (Craft & Role)
- Целеполагание и результат: понятно ли из файлов, какой осязаемый бизнес-результат агент сдаёт владельцу?
- Полнота инструкций: достаточно ли агенту знаний для автономной работы в своей нише? Нет ли пробелов в сценариях?
- Tone of Voice и системные промпты: отсутствует ли роботизированная канцелярщина? Насколько точно язык соответствует задаче?
- Защитные границы: зафиксировано ли, чего агент НЕ имеет права делать без подтверждения владельца?

### Блок 2. Инженерия и инфраструктура (Engineering)
- Работоспособность кода: наличие синтаксических ошибок, устойчивость к сетевым сбоям, тайм-ауты, повторы запросов.
- Синхронность с API и схемами: соответствует ли код реальным контрактам (Swagger, OpenAPI, XSD-схемы).
- Безопасность данных: отсутствие хардкода токенов, ключей, паролей (проверка выноса в .env/секреты).
- Валидация выходов (Exit Gates): наличие механизмов проверки итоговых данных перед сохранением/публикацией.

### Блок 3. Аудит чистоты и структуры (Hygiene & Bloat Check)
- Паразитный контекст (Context Bloat): файлы, раздувающие контекстное окно LLM без смысловой нагрузки.
- Мёртвые файлы и мусор: забытые черновики, дубликаты одних и тех же инструкций под разными именами, старые логи.
- Забытые тестовые артефакты: сырые JSON, временные выгрузки, случайно оставшиеся в рабочих директориях.
- Архитектурный дрейф: папки или модули, не относящиеся к роли агента (например, попытки агента решать чужие задачи).

## 4. Формат итогового заключения Codex

1. **ИНВЕНТАРИЗАЦИЯ ПРОЕКТА** — общее число проверенных файлов и папок; карта проекта (дерево) с кратким назначением каждого раздела.
2. **ТАБЛИЦА ЗАМЕЧАНИЙ** (CRITICAL / WARNING / TRASH-REDUNDANT).
3. **СПИСОК «ЧТО УДАЛИТЬ ПРЯМО СЕЙЧАС»** — точные пути к файлам и папкам.
4. **ИТОГОВЫЙ ВЕРДИКТ** — READY или ACTION REQUIRED.
